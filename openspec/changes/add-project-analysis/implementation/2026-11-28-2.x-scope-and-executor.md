## 问题与实测结论

### 1. rc.2 的 `restrict` 只裁剪「继承」工具

`@deepseek-ai/dsh-tools` 0.2.2-rc.2 的 `view(scope)` 把被查看 scope 的 **own 层**注册排除在限制之外，只对 `global + 祖先层` 的工具应用各层 `restrict`（`src/index.ts` 的 `view()`；docstring 写「scoped registrations stay visible」）。派生结论：

- 在 **preset 作用域**注册分析工具、又在同一 preset 作用域装 `restrict({allow: [...]})`，四个工具会被当成后代 Agent 的继承项一并遮掉。真宿主对照：probe preset（原生执行器 + `restrict({allow: []})` + 能力模块都在 preset scope）创建的分析 Session 可见工具为 `[]`。
- 分析工具注册在**分析 Session 自己的 agent scope**时属于该视图 own 层，不受 preset 的 `restrict` 影响；全局继承工具仍被遮掉。真宿主对照：同一 `restrict({allow: []})` 下，在 agent scope 注册四个能力后，分析 Session 恰为四个允许名，普通 Session 为 0 个分析能力。

因此实现取「preset 只声明原生执行器 + 分析作用域守卫/限制/准入，分析能力由 Host 在分析 Session 的 agent scope 注册」。这与 design「分析能力在专用作用域注册、执行器和守卫在首次派发前就绪」的边界一致；「专用作用域」按实测落为分析 Session 的 agent scope，而不是 preset revision 共享层。`analysis-scope.ts` 的 `restrict` 相应从 `allow: [四个允许名]` 改为 `allow: []`（只裁剪继承工具），四个能力名仍由守卫允许集兜底。

### 2. Host 侧执行前核对

新增 [analysis-execution.ts](../../../../packages/project-plugin/src/host/analysis-execution.ts) 的 `verifyAnalysisExecution(tools, agent, binding)`，只读、不注册、不执行工具，依次核对：

1. 绑定存在、已持久化、未终止，且实际 Agent 的 `id` 与绑定 Session 一致；
2. 实际执行器是 `NativeToolExecutor`（rc.2 的 `selectExecutor` 是实例私有方法，按最小运行形态读取；方法缺失/抛错/类名不符均 fail-closed，分别给 `analysis-executor-unverifiable`、`analysis-executor-unavailable:*`、`analysis-executor-not-native:*`）；
3. 该 Agent 的可见工具**精确等于**四个允许名（多出继承工具或缺失能力都给 `analysis-tools-mismatch`）；
4. 守卫已装、按真实 Agent 的作用域链求值：未允许工具必须被拒，允许工具不得被误拒；绑定未进作用域注册表时给 `analysis-binding-not-registered:*`。核对时绑定可能尚未把 `protected` 置 true，守卫返回 `analysis-execution-unprotected` 属预期中间态。

Host 的应然顺序：创建 Session → 在 agent scope 注册四个能力 → 登记未保护绑定 → `verify` → 通过后推进 `protected` → 再 `verify`（或直接以保护态复核）→ 才派发首条消息；任一步失败都不派发。

### 3. 真宿主证据（隔离 profile）

命令/原始输出：`/tmp/dsh-2x-probe/harness-2x-scope-final.mjs` → `r3-scope-registration.out`（不入库）。用 `--patch` 停用旧的全局测试夹具后：

- 分析 Session（`cona-project-analysis`）执行器 `NativeToolExecutor`；注册能力前可见 `[]`，注册后恰为四个允许名。
- `verify`：能力注册前 `analysis-tools-mismatch:missing=…`；注册后未保护/已保护均 `ready:true`；无能力的第二个分析 Session 仍 `missing=…`。
- 守卫：允许工具 `ALLOW`；`bash`、`run_code` 均 `analysis-tool-not-allowed:*`。
- 普通 Session：可见分析能力 0 个、共 45 个原有工具；直接调用分析工具返回 `unknown tool`；`verify` 返回 `analysis-tools-mismatch` 并列出 45 个 unexpected 工具。
- PTC Session：执行器 `PtcExecutor`；`verify` 返回 `analysis-executor-not-native:PtcExecutor`。
- 真实分派（`tools.execute`）：分析 Session 的允许工具成功执行（夹具输出 `agent=实际 SessionId`）；`bash`/`run_code` 在正文前被守卫拒绝；普通 Session 调用分析工具为 `UNKNOWN_TOOL`。
- `agent/pre-step`：错误 `rpcId` → `turn/end blocked` 且 0 个 `step/start`；正确 `rpcId` → 进入第 1 步；本隔离 home 无模型凭证，回合以 `MISSING_CREDENTIAL` 结束（环境事实，不是产品结论）。
- 终态绑定：`verify` 返回 `analysis-terminal`；允许工具调用同样被 `analysis-terminal` 拒绝。
