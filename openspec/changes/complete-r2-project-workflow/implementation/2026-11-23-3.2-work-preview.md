## 结论与关键决定

面板路径无法预知宿主消息的 `rpcId`（它由 DSH 在用户发送消息时生成），原先 `startWork` 强制要求 `rpcId`，导致“从接续摘要发起工作”在真实宿主里无路可走。本批把确认语义补成两条明确路径：

| 路径 | 确认方式 | 匹配规则 |
|---|---|---|
| 工具/测试既有路径 | `startWork({workIntentId, rpcId, sessionId?})` | 按消息 `rpcId`（可再限定会话）匹配 |
| 面板路径（本批新增） | `startWork({workIntentId, sessionId})` | 只匹配该会话的下一条用户消息消费 |

两条都要求至少一个可匹配身份（缺 `rpcId` 且缺会话直接 `operation-mismatch`），绑定仍只在 `observeConsumed` 的真实消费边界形成；运行建立后其他消息 `unmatched`，不会改写绑定。同会话多个待执行意图同时命中 → `ambiguous-intent` + `blocked`，不建运行。

## 已知边界

- H 层（干净 profile 把 B 设为配置实例、从卡片选会话确认、在真实会话发送消息形成绑定、Agent 工具读取与预览一致、旧验证标待核对）随 5.4 实测。
- 会话域确认只在「该会话下一条用户消息」上生效；确认后若用户在该会话先发了无关消息，绑定会落到那条消息上（这是“下一条即生效”的语义）。需要严格对应某条消息时仍用 `rpcId` 路径。
- 预览的依赖只列端点 id 与标题，不注入整棵树；目标节点被外部移除时以 `known=false` + `unverified` 呈现，不静默改写。
- 工作入口的“配置实例”判定来自注册表注入的 `configured.instanceId`；同机多配置实例不在本阶段范围。
