# R2 收尾设计

2026-11-22 双审确认通过。项目树、模板、Git 交换与新环境接续仍用同一个项目做联合验收。本文的「配置实例」指宿主启动时用于 WorkRun 和项目工具的实例。「浏览实例」可以是任一可访问的已登记实例。「完成条件」统一指节点的 `completionCriteria`。 [提案](proposal.md) · [用户裁决](review.md#L86) · [矩阵](validation-matrix.md)

## 1. 公开资料、Git 与位置迁移

### 接入与刷新

复用 `SourceService`、实例注册表及资料指纹。只读预览规范资料根、项目、格式、Git 跟踪状态和仓库声明。确认后登记。同项目的不同规范根各有自己的实例、`repositoryId` 映射、聊天、WorkRun 与回执。公开资料可读取历史摘要与验证。工件按当前实例的映射、相对路径和真实文件范围复核。

刷新在实例队列及本机写入锁内复查规范根、Git HEAD／工作区、原有效观察和候选头及其全部正文。比较预览与接纳时的头哈希、索引与正文清单及 Git 观察。验证成功才接纳完整快照。内容变化按实际指纹与本机双修订区分，外部追加记录只推进状态修订。切分支、回退与定位变化按源代际隔离。失败保留原有效快照及草稿。Git 观察只读。具体诊断如下。

| 判据 | 诊断与恢复 |
|---|---|
| 有未合并条目、头内存在冲突标记或解析后依赖成环 | 分别为 `git-unmerged`、`source-conflict-markers` 或既有依赖环诊断。修复后显式重取 |
| 某个原发布记录 ID 不在候选索引，或同 ID 的正文哈希被改写 | `source-index-loss` 或 `source-record-rewritten`，列出差异并停写。候选 HEAD 与先前观察属于同一已映射仓库，存在可验证的分支切换或回退，且候选公开头和所引正文逐字节对应历史 commit 树时，允许预览并显式确认该历史快照。重读失配时重新确认。无该证据时修复资料后重取 |
| 候选引用的正文不存在、当前字节与索引不符、预览和接纳时观察值改变 | 分别为 `source-body-missing`、`source-body-hash-mismatch`、`source-observation-changed`，列出记录或观察差异并要求重取 |
| 未知格式或源项目身份变化 | 沿用格式或身份诊断，保留最后有效视图及原资料 |

合法的未提交内容可经同样校验接纳。任何旧请求都要通过当前基线检查。已提交旧回执只说明原操作的历史结果。

### 迁移、排他与恢复

迁移保留实例身份，更新有效定位及源代际。预览列出原根、目标、当前格式、跟踪状态和本机引用。确认前处理草稿、在途发布及未消费、活动或终态未知的项目工作。应用服务先进入受影响实例的 `InstanceCommandQueue`，再取得与登记共用的本机根写锁。命令发布、源刷新、工作启动及登记按同一顺序重新核对登记和迁移标记。复制过程中到达的实例命令排队或收到 `migration-in-progress`。进入队列后重查迁移状态和当前代际，旧请求不得改投新的源。其他进程的本机持久写路径遵守同一锁和持久标记。外部文件编辑按源和目标的重新观测处理。

| 持久位置 | 最小契约 |
|---|---|
| `registry.json` | 读取旧 schema 1 及新 schema 2。开始首笔迁移时以检查过的原子替换提交 schema 2，完整保留登记项。每笔迁移记录 `operationId`、`requestDigest`、`instanceId`、`projectId`、规范 `from` 与预期代际、规范 `to`、新代际、目标候选位置与所有权标识、原头和公开文件清单哈希、状态与原回执。目标占用用未结束迁移和有效实例共同判断。旧读者遇 schema 2 停写 |
| `state.json` | 保持现有聚合 schema 1，已有聚合按原样读取。登记切换后检查并更新 `source`、源观察及状态修订，保留聊天、回执与规划版本。登记和聚合存在过渡差异时先恢复，实例保持写隔离 |

迁移状态为 `prepared` → `target-ready` → `switched` → `committed`。未切换且可证明无发布时可记 `canceled`。未知状态保留最近持久状态和具体诊断，以实际登记和文件核对。`prepared` 先冻结请求和源清单。要求目标与源无重叠、未被占用。采用独占建立的目标侧临时目录及受检查的目标保留，逐字节验证公开头和正文，确认目标未出现外部内容后装入。装入前后都防止覆盖既有目标。`target-ready` 只在候选和目标已验时写入。写入 `switched` 时在同一次登记替换中改活动根及新代际，这是唯一切换点。聚合与当前目标核对及回执持久化后才开放新源。

重启时先核验登记记录、候选及目标实际字节。旧根仍有效时仅继续可证明归属原操作的复制，或取消可证明未切换的操作。取消只清理有所有权证据且内容核对过的候选。切换后只补齐聚合和原回执，重复确认核对原请求摘要。无法证明归属或发生不一致时保留现场并停写。完成后旧根原样保留，从实例入口发出的新写只落新根。外部编辑旧根不会刷新新根。用户显式重新接入旧根时登记另一实例。用旧根配置重启时按已登记实例的有效定位核对；旧根已登记为另一独立实例时要求按实例明确选择。迁移后重新核对代码映射、引用和草稿，旧操作按原回执归属查询。

## 2. 共享命令、树与用户模板

### 命令与发布契约

每个请求提交一个领域动作。`ProjectCommandService` 对原信封新增以下分派，复用 `requestDigest`、`allocateIds`、候选校验、持久意图、回执及同源快照。字段中出现的节点、模板和证据 ID 都以当前实例的有效资料解释。既有客户端继续使用现有字段。

| 命令 | 业务载荷及候选 | 调用方 |
|---|---|---|
| `group-nodes` | 同父级的 `nodeIds`、组节点内容、`anchorId`。创建一个组并移动原子树 | owner |
| `merge-nodes` | `keepNodeId`、同父级 `sourceNodeIds`、保留节点字段补丁及每条受影响依赖的保留或重接。移动后代、取消来源，并生成一条结构化替代记录 | owner |
| `copy-subtree` | `nodeId`、目标 `parentId` 和 `anchorId`、明确接入的外部依赖。按源子树顺序分配新 ID | owner |
| `undo-plan-edit` / `redo-plan-edit` | 原 `targetOperationId` 和确认预览指纹 `previewDigest`。服务端从已核对的私有历史与当前基线重算逆向或重做候选 | owner |
| `insert-user-template` | `templateId`、`versionRecordId`、`contentHash`、`parentId`、`anchorId`。`parentId` 必须是现有父节点。按模板键顺序分配节点 ID | owner 或明确授权的 Agent |
| `enable-project-roadmap` | 从当前 v1 基线创建空的 v2 里程碑集合。拒绝对其他格式执行 | owner |
| `set-milestone` | `nodeId` 与 `deliveries`，`null` 表示取消里程碑标记。保持同一节点身份 | owner |
| `complete-milestone` | `nodeId` 及按完成条件提供的证据引用。提交完成状态与完成依据记录 | owner |

既有 `update-node` 继续用于目标及条件，手工拆分使用 `split-node`。`requestDigest` 覆盖规范化业务载荷、实例及基线。动态预览解析结果不得替换请求已确认的版本或锚点。已验证的提交用同操作号同载荷只返回原结果。已生成的节点和记录 ID、最终头、正文清单、修订及结果先进入持久意图，重启或回执丢失时按其核对。候选可包含规划和衍生记录。先准备正文，权威头一次发布；正文未被有效头引用时无可见业务结果。失败的子步骤整项拒绝。

分别比较规划指纹及索引增量。两者均无变化时保留头和规划修订，以既有状态回执记录该操作。仅增加记录时保留规划修订；规划确有变化时恰好增加一次规划修订，有衍生记录时状态修订也只增加一次。`OWNER_ONLY_COMMANDS` 或等价拒绝表包含新增 owner 命令。Agent 仅按第 3 节获得独立授权。Host 正常保存状态仍要求原回执及同源回读。 [提交规范](../../specs/project-command-commit/spec.md)

### 批量编辑与结构化替代关系

分组、合并以同父级普通节点多选为单位。分组创建父节点，保持原子树 ID、相对顺序及依赖。拆分保留原节点条件及关系。合并保留获选节点，移入后代，按预览处理出入依赖。来源保持原 ID、原分支、聊天和历史，以已取消状态保留。复制保留标题、目标、条件和内部依赖映射，按确认选择外部依赖，新节点从 `todo` 开始。

合并在同一权威头加入 `plan-change` 记录，精确摘要前缀为 `[cona:replacement] `，版本首行为 `<!-- cona:replacement v1 -->`。撤销发布同型记录解除关系。数据来自当前命令候选，索引的 `subjectNodeIds` 覆盖受影响的来源和保留节点。公开正文遵循下方的记录约定。读端仅从经过正文哈希验证的已发布索引按顺序投影，核对清除记录的来源和记录 ID、每个来源的当前关系、当前节点是否取消及替代链无环。新操作拒绝重复活跃来源和环。旧 v1 资料没有该记录时只显示原节点状态，无推断的替代目标。活动替代关系失效时展示待核对和原记录 ID。路线图始终保留原交付引用，显示待核对及可定位的替代目标。撤销在同一候选恢复原状态、结构和依赖并追加清除记录。重做产生新的替代记录，旧历史保持可查。

替代正文是以下两个互斥的对象之一。每种形状均要求所有列出的字段，拒绝额外字段。

| `kind` | 字段及约束 |
|---|---|
| `replace` | `version: 1`、`kind: "replace"`、`sourceNodeIds`（非空且不重复的节点 UUID 数组）、`replacementNodeId`（当前项目节点 UUID，不得出现在来源数组中） |
| `clear` | `version: 1`、`kind: "clear"`、`clearsRecordId`（已发布且在当前索引中更早的 `replace` 记录 UUID）。解除该记录的全部关系，逐项核对这些来源当前仍指向该记录。指向其他记录、重复解除和部分清除均拒绝，原替代正文继续保留 |

### 撤销与重做

只对当前源且有逆向信息的 owner 规划编辑提供。覆盖节点字段、树结构、模板插入及 `set-milestone`。v2 启用、里程碑正式完成、记录发布、聊天和外部动作沿各自流程，普通状态操作继续按既有提交。旧回执无逆向信息时禁用入口并给原因。将受影响字段、关系、前后值、生成 ID、必要的替代记录及已核对原回执留在本机历史，跟随原回执保留，沿用其清理策略。当前版本没有单独的期限时与原回执一同保留。

确认后以新的操作号及基线提交，核对原操作方向、当前字段预期值、父与锚点、当前公开及私有引用、活动工作。无关编辑保留。出现后来使用的新节点、触碰字段、旧源或原关系变化时给冲突并保留现状。合法重做才可复用原生成 ID，仍需核对身份未被占用。验证及原替代记录均作为历史保留。

### 用户模板目录与版本

内置 `treePresets`、同步预设解析及 `insert-preset` 原信封保持兼容。用户模板用独立的异步 `listUserTemplates(instanceId)` 和 `getUserTemplate(instanceId, templateId, versionRecordId, contentHash)` 经 owner 实例读取边界装配。目录项为 `{source:"user", templateId, versionRecordId, contentHash, bodyLanguage, title}`。`templateId` 为沿用的 UUID，`versionRecordId` 为一次发布的记录 UUID，正文语言为一个明确的语言标签或 `und`。语言只是描述，正文按作者原文预览及实例化。既有 `PresetDescriptor` 和双语校验继续适用于内置模板。

保存用户模板复用 `append-record`，以 `[cona:template] ` 摘要和首行 `<!-- cona:template v1 -->` 标识，再提供严格 JSON `{templateId, title, bodyLanguage, nodes, dependencies}` 及可读 Markdown。节点用局部 `key`、`parentKey`（根为 null）、`order`、`title`、`goal`、`completionCriteria`，依赖用模板键二元组。正文仅含经确认的字段，验证重复键、树和依赖完整性、大小、字符及版本。通过 `plan-change` 记录兼容 v1；普通规划变化历史明确区分模板发布，接续与 WorkRun 默认上下文不会把模板记录当作实际规划变更或交付成果。模板目录仅收已发布且正文验证成功的记录版本。

提交 `insert-user-template` 时重读同实例索引及正文，精确核对三重身份、目标父组与锚点。版本不存在或移出索引返回 `template-version-unavailable`，身份或哈希不符返回 `template-version-mismatch`，严格描述无效返回 `template-invalid`，位置沿用现有错误码。两类模板的 `parentId` 都必须是现有父节点，`null` 及缺失父节点返回 `parent-not-found`。失败保留原草稿。预检失败不分配供发布的候选，已准备候选按原生成批次与回执核对，不重新解析模板。保存模板及插入分别出具回执。 [树编辑规范](specs/project-tree-editing/spec.md)

## 3. 本机聊天与配置实例上的项目工作

浏览实例可由 owner 创建、复用、关联、解绑和打开本机实际 Session，检查工作区与实例归属。接续摘要提供显式本机重绑。导航保持原 WorkRun 及发送状态。概览明确显示浏览实例的项目工作入口不可用，宿主继续以启动配置确定项目工具与事件归属。联合验收另用干净 profile／home 将工作副本 B 配为配置实例，先核对公开与本机关系，再由可信请求发起工作。

新工作显式确认会话、节点集合、意图及动作。同一聊天的第三个关联节点不进入两个选定目标的写范围。预览上下文列出目标、条件、直接依赖、约束、规划基线、已有决定、近期成果及验证、遗留和下一步，标明用户确认、建议及待核对项。可信消费或执行边界建立 WorkRun。旧会话和迟到请求继续按原绑定处理。

在 `WorkAction` 和 `commandAction` 中加入 `move` 与 `insert`。`project_apply` 的 `PLANNING_TYPES` 增加 `move-node`、`insert-preset`、`insert-user-template`。相应命令从静态 owner-only 拒绝集合移出，仍须通过可信 WorkRun 路径。`commandTargets` 对结构命令从当前计划解析影响范围：移动包括子树的既有节点、源和目的父节点、锚点及因归一化而编号变化的同级节点。插入包括目标父节点、锚点和已存在且编号变化的同级节点。`rootGroup` 只用于根组内重排，需用户在允许 `move` 的 WorkRun 中单独授予。内置和用户模板均只能插在现有父节点之下。Host 对 `insert-preset` 或 `insert-user-template` 的 `parentId: null` 在目标范围求值与候选分配前返回 `parent-not-found`，即使 WorkRun 已明确获得 `insert`、精确模板版本和根组重排许可。owner 走相同位置规则。`insert` 绑定同时冻结用户确认的模板来源与精确版本（用户模板包含记录 ID 和哈希）。旧绑定缺结构权限时按空授权读取。

应用层用同一计算在预检与提交时校验作用范围、动作、版本及基线。缺动作继续返回 `forbidden` 及明确的缺失动作。位置越权返回 `structure-scope-denied`，缺根组许可返回 `root-group-not-allowed`，模板许可不符返回 `template-not-authorized`。范围之外可留建议，规划保持。生成节点不自动加入当前目标。Agent 自身合法提交沿现有规则推进绑定版本；owner 改变规划后，原运行可继续执行和读，进一步写规划需在该运行结束后显式发起新工作。 [会话增量规范](specs/project-conversation-context/spec.md)

## 4. v2 交付关联与里程碑目标视图

### 公开格式与变换保留

原 v1 schema、canonical 字节和向量保持。v2 投影覆盖 `{schemaVersion, project, plan}`，`schemaVersion` 为 2。`plan.roadmap` 只含 `milestones`，每项为 `{nodeId, deliveries}`，交付项为 `{kind:"node", refId}` 或 `{kind:"record", refId, contentHash}`。里程碑按 `nodeId`，同一里程碑内交付按 `(kind, refId)` 依 v1 UTF-16 规则排序，重复项拒绝。v2 schema、向量、独立复算及导出格式说明随包分发。

普通编辑保持原格式。首次启用 v2 由 owner 预览兼容影响，显式确认后创建空里程碑集合。拒绝旧读者覆盖未知格式。所有规划变换从原 `Plan` 构造输出，只有明确的里程碑编辑或其逆向／重做能改动已知 v2 里程碑扩展；结构编辑触及里程碑节点或已发布引用时发生的变动另行预览核对，非法结果不发布。v1 路径不补扩展字段。`update-node`、`add-nodes`、`split-node`、`set-dependencies`、`set-node-status`、`move-node`、两种模板插入及新批量命令和逆向操作全部有保留测试。按规则要求更改里程碑时只写目标里程碑的公开字段。

### 生命周期与完成证据

里程碑所属节点 MUST 存在，外部删除该节点而留下里程碑条目时拒绝接纳，给出可诊断的 `milestone-node-missing`。取消或替代节点仍保留里程碑及原交付，视图显示历史和待核对。新交付只引用同项目存在的其他节点或哈希精确匹配的已发布成果，拒绝自引用、重复项和不可解析的新关联。已保存的交付来源后来缺失、取消、被替代或内容哈希改变时保留原引用并显示原因。接纳外部修改时将新增／改变的交付同最后有效规划比较；新增的失效引用停写，既有引用可作为待核对接纳。干净接入可显示形状有效的历史引用及诊断。删除里程碑标记或修订交付由用户显式提交。

正式完成使用 `complete-milestone`。其条件列表不得为空。`evidence` 逐项包含 `criterionIndex`、精确 `criterionText`、已发布验证 `recordId` 和 `contentHash`。同一记录可覆盖多条明确选择的条件；工具仅能核对结构、证据状态、范围和版本，owner 确认每条实际对应关系。每项证据要求 `verification.status:pass`、`subject` 指向该节点、`subjectVersion` 精确等于确认时 v2 规划指纹、`scope` 可供查阅。完成候选以新状态复算指纹，同一权威头加入 `verification` 记录，精确摘要前缀为 `[cona:milestone-completion] `，`verification.status` 为 `pass`，`subject` 指向里程碑节点，`subjectVersion` 为完成后的指纹。正文按下方公开约定保存输入基线与逐项条件及证据。`set-node-status` 对里程碑的新完成请求返回 `milestone-evidence-required`。为已有 `done` 的普通节点标记里程碑前先明确调整状态，再按专用动作核对。改变已完成里程碑的条件或交付会要求先重新打开并补验。其他规划变动后，原状态和证据保留为历史，界面按受检版本提示是否仍适用。

完成记录的版本首行为 `<!-- cona:milestone-completion v1 -->`。正文 JSON 是严格对象 `{version: 1, milestoneNodeId, inputPlanVersion, evidence}`。`milestoneNodeId` 为节点 UUID，须匹配索引的验证主题及记录主体。`inputPlanVersion` 使用 `sha256:<64 位小写十六进制>`，表示完成命令核对的输入规划。`evidence` 按完成条件原顺序列出 `{criterionIndex, criterionText, recordId, contentHash}`，索引从 0 开始连续，`criterionText` 保存原文。`recordId` 为已发布且在索引中更早的证据记录 UUID，`contentHash` 为其正文哈希。外部校验复查每项输入证据的索引、实际正文、`pass` 结论、主题和输入规划版本，并对照完成记录索引的受检版本。旧规划的完成记录按原条件和版本保留。当现有证据被移除或哈希改变时，只显示可追溯的历史与待核对诊断。

仅从 v1 启用 v2 就会产生新规划指纹。旧验证继续按原 `subjectVersion` 显示为 v1 历史证据，不覆写结论，也不计为当前 v2 完成依据。普通树或里程碑改动后以新指纹判断当前性，原引用和验证记录可追溯。交付关联不会生成执行依赖或完成状态。

### 两类公开记录的正文与互操作

替代和完成记录均使用 UTF-8、无 BOM。版本首行后紧接一个标为 `json` 的围栏代码块，解析严格 JSON，拒绝重复键、未知版本、未知字段和非安全整数。代码块后为从同一结构生成的可读 Markdown。读取先校验普通公开索引与实际正文哈希，再按 `kind`、精确摘要前缀和版本首行识别。匹配前缀但正文无效时报告记录 ID、字段和原因，停止依此推导替代关系或完成依据。历史资料中的普通记录保持原义。

随包并向资料根发布两类独立正文 schema、版本说明、正反例及公开验证命令说明。独立校验器从 `project.json` 出发读取索引引用正文，按识别出的 schema 验证，再按索引顺序校验引用、解除链和证据版本，无需 DSH 或本机状态。任务 2.2 和 4.3 分别验收两类资料的可移植工件。
