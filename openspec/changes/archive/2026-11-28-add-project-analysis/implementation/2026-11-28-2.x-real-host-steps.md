# 2.x 真宿主实测步骤（交用户在真终端执行）

前置：本次改动尚未提交／同步。请先在真终端启动一次固定 DSH `0.2.2-rc.2`，确认插件 `dsh-cona-project` 仍正常加载；若宿主启动失败，按[阶段实施记录](2026-11-28-2.x-host-connection.md#风险与回滚)移除 `cordis.patch.yml` 的第二个 `- insert:` 块即可恢复。

## A · preset 注册与加载（2.1）

1. 用隔离 profile 启动 DSH `0.2.2-rc.2`，加载本插件包。
2. 查宿主日志，确认 `agentPresets` roster 含 `cona-project-analysis`，且无重复 ID／声明解析失败诊断。
3. 特别核对三处 keyless 无法证明的接点：
   - `dsh-cona-project/analysis-scope` 子路径能否被 cordis-plugin-loader 解析为包导出；
   - `analysis-scope.ts` 的 `ctx.effect` 在 cordis scope 内是否可用（不可用会走 fail-closed 并返回 `analysis-prestep-failed` 或 loader 报错）；
   - `ctx.on('agent/pre-step', ...)` 在 preset scope 内是否收到事件。
4. 用 `SessionController.create({ workspaceId, agentPreset: 'cona-project-analysis' })` 新建会话（省略 `sessionId`），核对实际 preset、工作区挂载、消息认领与宿主终态。
5. 负例：临时制造 ID 冲突／声明解析失败，核对概览显示分析执行不可用且未派发分析消息。
6. 证据：宿主日志片段、roster 快照、实际 Session 身份与 preset；记入矩阵 A03/A05。

## B · 执行器选择与 PTC 对照（2.2）

1. 普通原生 profile：分析 Session 应显示原生执行器；普通 Session 保持原组合。
2. 启用 PTC 的隔离对照 profile：分析 Session 仍走原生执行器，`run_code` 入口无法调度；普通 Session 仍用 PTC。
3. 合成文件正反对照：
   - 分析 Session 调 `run_code`／通用代码／Shell／编辑／代理／公开写入 → 正文开始前拒绝，正文未进入；
   - 范围外合成文件内容未返回；
   - 范围内外测试文件字节未变。
4. 分别记录部署的文件／进程沙箱模式，区分「guard 拒绝工具调用」与「沙箱拒写」两层证据；单有文件未变化不足以证明没有代码执行。
5. 证据：两个 profile 的执行器标识、工具调用结局、文件哈希前后对比；记入矩阵 A04/A05。

## C · 保护不可用与历史会话（2.3）

1. 注入四类失败：原生执行器无法核对、守卫不可用、绑定未持久化、启动响应丢失。核对后台不派发无保护请求。
2. 正常完成、中断、换源、重启后，向原 Session 输入新请求；核对 `agent/pre-step` 拒绝、步骤未入模型、旧绑定读取／保存被拒、报告仍可回看。
3. 证据：宿主 turn/step 日志、请求未入模型的事实、历史报告可回读；记入矩阵 A03/A07。

## 回填约定

- 只把实际跑到的分句改 `pass`；未跑到的保持 `untested`，不因同组其他分句通过而放宽。
- 每条 `pass` 附可复核证据位置（日志路径／截图／命令输出），不使用推测值。
- 三项任务 2.1–2.3 只有在各自矩阵行全部对应分句有证据后才勾选。
