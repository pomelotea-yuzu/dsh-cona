# R1 2.4 映射实测记录（2026-11-13 晚）

> 目标：用最小诊断插件分开实测真实 Remote invocation、owner principal、无 invocation 的 ToolRunContext，以及 queue／steer／迟到工具／取消／重启的消息与 turn 映射，交付映射结论。
> 方法：通过 Web 载体的真实 `/api` 通道驱动真实会话（浏览器 cookie 与 API cookie 都走同一 Gateway），不依赖浏览器控制台；结果以会话事件 log 与宿主日志为证。不是静态核对，也不是自报身份。

## 环境与命令

- profile：`cona-r1-test`（base + `@deepseek-ai/dsh-web-app` + 插件）；启动：`dsh --profile cona-r1-test --patch artifacts/r1-2.4-test/model.patch.yml --port 0 --no-open`。
- 模型 overlay：base 默认 `deepseek-official` 在本机 home 无 key，首轮实测 `turn/end error: llm-deepseek: no API key for provider route "deepseek-official"`；用 `--patch` 临时对齐 desktop 的 `deepseek-account / deepseek-flash`，不改 profile 文件。
- 宿主：Node v24.21.0（apply 日志与 probe 双向确认），DSH 0.2.2-rc.2；重启前 pid 17719，重启后 pid 17882。
- 驱动：`artifacts/r1-2.4-test/rpc.mjs`（token → cookie → `POST /api/<ns>/<method>`）与 `exp*.mjs`；会话 log 存 `artifacts/r1-2.4-test/page-<session>.json`。

## 为什么不走 Client 自动探针

上一轮提交的 Client 自动探针已回退，原因均为实测：

1. 洁净构建被破坏：`src/client/index.ts` 静态 import `lib/typert.remote-client.js`，而 tsc 先于 generate 运行；`rm -rf lib && pnpm build` 报 `TS2307: Cannot find module '../../lib/typert.remote-client.js'`。
2. 运行时必然缺模块：bundle 内保留 `require("@deepseek-ai/dsh-typert-protocol/remote-info")`，而 manifest 的 `dsh.client.inject = []`、boot graph 无该协议行；Client 模块表对未登记 external 直接抛 `require(...) missed the module table`。
3. 2.4 的 Remote 证据用真实 `/api` 载体已足够，无需为此扩大 Client 包（原方案还引入 746KB bundle 与 `rejectBuildOutputs: false` 的守卫放宽）。

## 实测结果

### A. Remote invocation（owner）

- 浏览器 cookie：`POST /api/conaDiagnostic/probe`，`payload={"args":{}}` → `{ok:true, value:{hasInvocation:true, peerPrincipal:{kind:"owner"}, service:"conaDiagnostic", runtime:{nodeVersion:"v24.21.0"}}}`。
- API cookie（`GET /connect?token=…&interactions=none`，302 到 `/api/remote.mux`）同样返回 `peerPrincipal:{kind:"owner"}`。
- `principalOfResult` 缺省符合协议：`principalOf` 对 owner 返回 `undefined`。
- 结论：本部署只有 owner 身份面；`principalOf` 为空不代表“无授权主体”，不能把它当作唯一授权判据。

### B. 工具侧 ToolRunContext（无 invocation）

会话 `session-b750b3bb-…`，模型真实调用 `cona_diag_context`（无参数）：

```
agentId: session-b750b3bb-ac0e-4e0c-be4a-250a74e5c1c2
callId: call_00_ET_od9Ph7WzBTD7hHOs9Jv89904
signalAbortedAtStart: false
signalAbortedAtEnd: false
waitedMs: 0
```

- `agentId` 等于 SessionId；`callId` 每次调用新生成。
- 工具执行上下文只有 `callId/rootCallId/agent/signal`（`packages/core/tools/src/contracts.ts:175-203`），没有 Remote invocation 或 principal——工具准入必须来自 agent/session 归属，不能靠 invocation 身份。

### C. queue（运行中入队）

会话 `session-e4104f44-…`：先发“调 delayMs=8000 的探针”，立即再发一条普通 prompt。

| seq | 事件 | 要点 |
|---|---|---|
| 3 | `agent/inbox/spliced target=next-turn` | A 进 inbox |
| 4 | `turn/start` | turn 1 开始 |
| 6 | `agent/inbox/spliced target=next-turn` | B 在 turn 1 运行中入队，不打断 |
| 22-23 | `tool/call` → `tool/result waitedMs=8001` | A 的探针完整执行 |
| 29-30 | `turn/end completed` → `turn/start` | turn 1 结束后 B 作为 turn 2 启动 |
| 36-37 | B 的 `tool/call`，新 callId | agentId 不变、callId 换代 |

结论：queue 是“投递到下一次 turn”，不打断当前 turn；被消费时以 splice removed 表示。

### D. steer（运行中改向，含迟到工具）

会话 `session-c5aa1582-…`：探针 `delayMs=15000` 执行中，在 tool/call 出现后发 steer。

| seq | 事件 | 要点 |
|---|---|---|
| 21 | `tool/call` args `{"delayMs": 15000}` | 工具在飞 |
| 22 | `agent/inbox/spliced target=next-step` | steer 不进 next-turn，而是等下一步边界 |
| 23 | `tool/result waitedMs=15001, abortedAtEnd=false` | **steer 不 abort 在飞工具**；结果照常落盘（迟到结果） |
| 25-27 | splice removed → `step/start` → user/message | steer 在 step 2 被消费 |
| 31 | `turn/end completed` | 同 turn 内改向完成 |

结论：steer 在 step 边界注入，不取消在飞工具；迟到的工具结果仍然进入同一 turn，随后被 steer 文案覆盖方向。归属仍是同一 agent/session。

### E. cancel（运行中取消）

会话 `session-b9058890-…`：探针 `delayMs=15000` 在飞时 `POST /api/session/cancel`。

| 证据 | 值 |
|---|---|
| 宿主日志 | `tool exec ... abortedAtStart=false abortedAtEnd=true waitedMs=112` |
| 会话 `tool/result` | `Error: tool call aborted`（宿主替换了工具自己的返回） |
| `turn/end` | `{"kind":"aborted","reason":{"kind":"user"}}` |

结论：取消信号到达工具（112ms 内），工具自行提前返回；宿主丢弃其结果并以 abort 错误收尾 turn。工具实现不能假定取消后结果仍会被采纳。

### F. 重启（resume 映射）

会话 `session-42b883bd-…`：重启前 pid 17719，调探针记录 `callId=call_00_lrgpFrGVWjy91ISxGkiz6614`；kill 宿主后用同一 URL 流程重起（pid 17882），对同一 session 再 prompt。

- 历史保留：重启后 `session/page` 仍返回旧 turn（seq 22 旧工具结果、seq 28 旧 turn/end）。
- 新 turn 探针：`agentId` 不变（仍是 `session-42b883bd-…`），`callId=call_00_DnZEkB2FNpoawSXGaP1T3875`（换代）。
- 结论：Host 重启不改变 Session 身份；agentId 可作为稳定绑定键，callId 只能标识单次执行。

## 映射结论（供第 4／6 段）

| 输入/事件 | 宿主事件 | 绑定含义 |
|---|---|---|
| prompt `mode:'queue'` | `agent/inbox/spliced target=next-turn` | 排队到下一 turn；不打断当前执行 |
| prompt `mode:'steer'` | `agent/inbox/spliced target=next-step` | step 边界改向；不 abort 在飞工具，迟到结果仍属于本 turn |
| 队列项消费 | `agent/inbox/spliced removedCount` + `user/message` | 消费点可观察，用于回执/幂等对齐 |
| 工具执行 | `tool/call` → `tool/result` | callId 单次；agentId=SessionId；无 invocation |
| 取消 | 工具 signal abort → `Error: tool call aborted`；`turn/end aborted/user` | 结果不可当作已提交 |
| 正常结束 | `turn/end completed` | — |
| 重启 | resume 同 Session；agentId 稳定、callId 换代 | 不得用 callId 当持久身份 |

## blocked / 未测

1. **non-owner principal（blocked）**：本部署只有 owner 身份面。`PrincipalMap` 仅定义 `owner`；唯一的非 owner principal 来自 `@deepseek-ai/dsh-experimental-liveshare` 的 `share-viewer`，需要独立部署的 Liveshare 服务与 OAuth。浏览器 cookie 与 `/connect` API cookie 都验证为 owner。不以自报身份伪造非 owner。
2. **agent 缺失／归属不唯一拒绝新绑定（blocked）**：R1 诊断插件没有绑定/准入层，工作站内也不会出现 agent 缺失的真实工具调用（实测 agentId 始终为 SessionId）。该判定属于第 6 段实现，届时用真实 Agent 复测。
3. **迟到工具跨 turn 到达**：本轮只覆盖“steer 期间工具结果晚于 steer 入队”和“cancel 替换结果”；turn 结束后才到达的工具结果未能构造，保持 untested。
