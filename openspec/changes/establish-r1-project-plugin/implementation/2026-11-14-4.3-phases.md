## 执行顺序（design §6 步骤 4–6）

| 阶段 | 动作 | 失败结局 |
|---|---|---|
| 候选构造 | 重读基线、变换、渲染候选头（不写文件） | `invalid-project`／`unsupported-format`／`plan-conflict`／`forbidden`，无副作用 |
| `prepared` | 落盘候选头全文、候选哈希、正文清单、预算结果、生成 id | `persistence-failed`，不写任何文件、不留记录 |
| `publishing` | 标记“可能已开始写文件” | `persistence-failed`，此时仍未写文件，记录标 `rejected` |
| 正文 | 逐条写不可变正文（先于头） | `conflict／not-published` → `rejected`；`unknown` → 待核对（停 `publishing`） |
| 资料头 | 替换并回读；`writeHead=false`（无业务变化）时跳过 | `not-published` → `rejected`；`unknown` → 待核对（停 `publishing`） |
| 回执 | 同一次聚合替换写入 `committed`、双修订、观察基线 | 未保存 → `pending-reconciliation(stage=receipt)`；`unknown-state` → 待核对（停 `publishing`） |
| 通知 | 提交后发送，异常被吞掉 | 不影响结果，回执可查 |

## 关键决定

1. **候选头全文进意图**。只存哈希不足以在恢复时判断“当前内容是否精确对应候选”；4.4 需要全文比对。
2. **未决阻塞而不是自动续写**。同实例存在 `prepared`／`publishing` 记录时，任何新命令返回 `instance-blocked`；同 `operationId` 重试也只返回待核对。续写与补回执是 4.4 的显式恢复动作。
3. **回执未落盘按待核对处理**。资料已经发布却返回“可重试的失败”会诱导重复执行，因此改为 `pending-reconciliation(stage=receipt)`。
4. **通知在提交之后**。设计明确“通知失败不得撤回或重复执行已提交事实”，实现为提交完成后调用、异常吞掉。
5. **`writeHead` 显式入意图**。无业务变化时不重写资料头，但回执与 `stateRevision` 仍要推进；这个决定必须在意图里可回看。

## 未覆盖（不得当作通过）

- **自动恢复**：崩溃后按候选核对、补回执、修订只推进一次 —— 4.4。当前未决只能人工核对，没有恢复入口。
- **unknown 隔离**：4.5；`publishing` 记录会阻塞新命令，但尚未提供只读诊断与显式解除。
- **真实宿主（H）**：阶段状态未在真实 Remote／工具入口下观察；通知流只是依赖钩子，尚未接 `ChangeNotificationPort`（第 5 段）。
- **断电**：仍无目录 fsync，未做突然断电试验。
- **发布中取消**：取消信号在文件替换后的处理未实现（6.x 的 cancel 语义）。
