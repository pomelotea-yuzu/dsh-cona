## 草稿与保存规则（design §8、tasks 5.2）

| 情形 | 行为 |
|---|---|
| 编辑目标或新增节点 | 生成草稿并记下当时的 `planVersion／planRevision／sourceEpoch`（之后刷新不改草稿基线） |
| 保存成功 | 清草稿 →（有原因时）追加 `plan-change` 记录 → 回读快照 → 标「已保存」 |
| `plan-conflict`／`source-changed` | 标「冲突：草稿已保留」，草稿与原因都不清空，**不标已保存** |
| `pending-reconciliation` | 标「结果待核对」，草稿保留，**原 operationId 保留** |
| 传输异常 | 结果未知：草稿保留、operationId 保留，重试不换 id |
| 原因记录写入失败 | 规划已保存但标「部分保存」，原因保留可单独重试，不谎报已保存 |
| 再次编辑 | 立即清除「已保存」 |

新增节点的 `order` 由同级最大值 +1 计算（资料要求同级有序），不在 UI 里让用户填。

## 关键决定

1. **控制器与渲染分离**：草稿与保存规则全在 `panel-controller.ts`，可脱离浏览器测试；React 组件只读状态、调方法。
2. **传输可替换**：面板只依赖 `PanelTransport`。当前实现走宿主 `/api` 载体（`payload.args = {request}`，2026-11-14 实测），后续换成 `ctx.remote.$mount` 生成的代理只需替换一个模块。
3. **冲突不自动合并**：R1 只保留草稿并提示，不尝试把草稿 rebase 到新基线（design §8 明示不自动合并复杂编辑）。
4. **原因记录后置**：规划命令成功后才追加 `plan-change`；两段式结果分别表示，partial 不标已保存。
5. **order 由应用推算**：UI 不让用户输入 order，避免同级冲突。
