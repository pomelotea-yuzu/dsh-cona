## 恢复分支（design §6 恢复表）

| 记录状态 | 核对结果 | 处理 |
|---|---|---|
| `prepared` | 可证明未进入发布 | 标 `rejected(not-published)`，保留 operationId，解除实例阻塞；重做需新命令 |
| `publishing` | 头哈希 == 候选哈希 且 每条正文哈希匹配 | 补回执 `committed`、`recovered: true`、`recovery: candidate-matched`；双修订取 `max(当前, 意图预算)` |
| `publishing` | 头哈希 == 原基线哈希 | `pending-reconciliation(stage=reverted)`：不能排除“发布后被回退”，不宣称未提交 |
| `publishing` | 既不匹配候选也不等于原基线 | `pending-reconciliation(stage=diverged)`：不自动覆盖 |
| `publishing` | 候选记录缺失 | `pending-reconciliation(stage=missing-candidate)` |
| `committed`／`rejected` | 历史 | 只返回历史回执，不重新应用 |

## 关键决定

1. **恢复只核对、不重放**。`recover` 不执行任何业务命令，只比对磁盘与意图；因此它无法被用来“换 id 重跑”。
2. **双修订用预算值取 max**。补回执时 `planRevision = max(当前, prepared.planRevision)`，重复恢复或恢复前后重启都不会把计数推两次。
3. **原基线哈希必须入意图**。只比较候选哈希无法区分“从未发布”和“发布后被回退”，两者都表现为“当前不是候选”；`originalHeadHash` 让后者明确落进 `reverted`。
4. **拒绝回执也走同一注入点**。`finishRejected` 现在接受 `hooks.state`，才能构造“停在 prepared”的中断现场，也让拒绝回执写入失败可观察。
5. **恢复仍需归属匹配**。`agent-work` 的回执不能被 owner 恢复；归属不符返回 `forbidden`。

## 实测证据

### 自动化

- 本地 Node v22.22.2：`test:run` **154/154**（4.3 的 148 + 6）。
- 宿主 Node **v24.21.0**：**154/154**。
- `pnpm check:ci` 退出码 0。

| 测试 | 断言重点 |
|---|---|
| prepared 恢复 | 记录停在 prepared（注入 publishing 与拒绝回执两次写失败）→ 恢复返回 `code=not-published`、`recovery=not-published`、资料不变、记录转 `rejected`；随后新命令可执行 |
| 候选精确匹配 | `committed` + `recovery=candidate-matched`，`planRevision=1`／`stateRevision=1`；`recovered=true`；再次恢复（新服务实例）返回 `recovery=history` 且修订不变 |
| 退回原基线 | 恢复返回 `stage=reverted`，修订不动，记录仍 `publishing` |
| 分叉 | 合法第三方内容 → `stage=diverged`，不覆盖 |
| committed 后回退 | 重试与 `getReceipt`、`recover` 都返回历史，资料保持回退后的内容（未重放） |
| 归属守卫 | 工具提交的回执由 owner 恢复 → `forbidden`；不存在 → `not-found`；无上下文 → `forbidden` |

### 手工 CLI

```text
command run --command '{"type":"update-node", …}'   → committed（planRevision 1）
# 模拟 Git 回退：把 project.json 换回提交前字节
command recover --operation <同一 id>
→ committed, replayed:true, recovery:"history"
diff 原字节与当前资料 → 相同（恢复没有重新应用修改）
```
