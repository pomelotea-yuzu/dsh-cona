## 关键决定

1. **幂等查询在冲突判断之前**。先按 `(instanceId, operationId)` 查记录：同摘要同归属 → 返回历史结果（`replayed: true`）；摘要不同 → `operation-mismatch`；归属不同 → `forbidden`；`pending` → `pending-reconciliation`。查询本身仍需当前读取资格。
2. **意图先于发布**。先写 `status: 'pending'` 的操作记录（含稳定生成 id 与原始基线），写不进去就不发布任何资料；这是"意图失败不发布"的最小实现，完整的 `prepared／publishing／committed` 阶段留给 4.3。
3. **稳定生成 id 落在意图里**。`add-nodes`／`split-node` 的节点 id、`append-record` 的记录 id 在意图阶段生成并保存；重放返回同一批 id，核对时也可复用。
4. **原始基线必须可回取**。摘要包含 `expectedPlanVersion／expectedPlanRevision／sourceEpoch`，所以"原样重试"必须用原值；记录保存这三项，CLI 在 `--operation` 重试时自动取回。
5. **无业务变化只推进状态修订**。规划命令变换后 `planVersion` 未变时：不重写资料头、`planRevision` 不变、`stateRevision +1`、保存回执；重试不再推进。
6. **明确拒绝也留回执**。防止同一 operationId 被反复执行；回执写入失败不回滚"拒绝"事实（没发布任何内容，重试安全）。

| 稳定生成 id | 回执 `recordId` 与意图 `generated.recordId` 一致；重试返回同一 id；原始基线三项可回取 |

### 手工 CLI（修复前后对比）

修复前，`--operation` 重试会重读当前基线，摘要变化被误判为换参数：

```text
第一次 → committed (planRevision 1, stateRevision 1)
原样重试 → rejected operation-mismatch   ← CLI 默认取当前基线所致
```

修正为“优先取回记录里的原请求基线”后：

```text
第一次   → committed, planRevision 1, stateRevision 1
原样重试 → committed, planRevision 1, stateRevision 1, replayed: true
换参数   → rejected operation-mismatch
```

这不是放宽校验：服务端仍按 envelope 摘要比对，只有真正原样的请求才重放。
