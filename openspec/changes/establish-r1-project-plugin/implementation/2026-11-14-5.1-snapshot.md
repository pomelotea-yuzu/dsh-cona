## 一致读取算法

每次 `read`：

1. 核对可信上下文（与命令入口同判据）、连接代际（旧代际 → `stale-connection`）、隔离标记（→ `unknown-state`）与注册表实例；
2. 读本机聚合（修订、源代际、未决操作）；
3. 读资料头 + 全部引用正文并逐条复核哈希（`readSourceBaseline`）；
4. 再读一次本机聚合；两次之间修订／源代际变化 → 重读；注册表代际与聚合不一致 → 重读或 `source-replaced`；
5. 存在 `prepared／publishing` 未决发布 → 重读（发布落定前不产生“已保存”快照）；
6. 订阅水位或调用方下限高于本机修订 → 继续追读；
7. 重试耗尽 → `unsynced`（`unstable／pending-operation／source-replaced` 之一），**不返回树**。

拒绝路径不返回半截快照：正文哈希不符 `body-hash-mismatch`、正文缺失 `body-missing`、冲突标记 `source-conflict-markers`、schema／未知字段 `unsupported-format`、其余结构问题 `invalid-project`，均带 issues。

同步状态：

| 情形 | `sync` |
|---|---|
| 磁盘头与本机最近观察一致 | `synced`，`basis: local-observation` |
| 本机尚无观察基线（登记后未刷新） | `synced`，`basis: current-read`（明示未构成已验收基线） |
| 磁盘头与本机观察不一致（外部编辑未刷新） | `not-synced`，`reason: source-drift`，`requiresRefresh: true` |

三种情形都要求读取期间两次聚合一致、正文逐条哈希通过；`not-synced` 仍给出一份“磁盘一致”的内容并显式标未同步，面板不得据此显示“已保存”。

## Remote 契约（Cona 自有，不宣称 DSH 已有方法）

命名空间 `conaProject`（design §5）。两个方法都走 UI Remote owner 判据：必须是宿主生成的 `ctx.invocation`、peer 主体 `owner`；`principalOf()` 为空不作为授权依据；工具入口在 R1 不提供读取工具（6.3 再补）。

### `conaProject.snapshot(request)` → `SnapshotResult`

```ts
request = { instanceId: string; connectionGeneration: number; minStateRevision?: number }
```

| 结果 | 含义 |
|---|---|
| `{status:'snapshot', snapshot}` | 一致快照；`snapshot.sync.status` 区分 `synced／not-synced` |
| `{status:'unsynced', reason, attempts, detail}` | 重试耗尽仍无法一致；无树，客户端应显示未同步并等待下次通知 |
| `{status:'rejected', code, message, issues?}` | `forbidden／operation-mismatch／stale-connection／unknown-state／binding-expired／unsupported-format／invalid-project／body-hash-mismatch／body-missing／source-conflict-markers` |

`snapshot` 字段：`projectId, instanceId, sourceEpoch, schemaVersion, planVersion, planRevision, stateRevision, connectionGeneration, sync, project, tree, dependencies, records, summary, local, readAt`。`tree` 为 DFS 扁平序（父先于子、同级按 `order`、`id`）；`summary` 只由同一份 `tree／dependencies／records` 派生。

### `conaProject.follow(request)` → `RemoteStream<StreamEventView>`

```ts
request = { instanceId: string; afterStateRevision?: number }
```

首个事件固定为 `ready`：`{kind:'ready', instanceId, projectId, sourceEpoch, stateRevision, planRevision, connectionGeneration, at}`。其后为 `committed／refreshed／source-replaced`；`source-replaced` 之后 Host 结束该流。Host 以 Typert `RemoteStream` 输出，Client 得到 `RemoteStreamHandle`，`dispose()` 取消订阅。

服务层 `follow` 先在当前聚合上建立水位（`max(聚合 stateRevision, 客户端 afterStateRevision, 订阅水位)`），再分配代际；同实例新代际会关闭旧代际订阅。

### 客户端顺序（固定）

1. `follow` → 拿 `ready`（记录 `connectionGeneration`、`sourceEpoch`、`stateRevision`）；
2. `snapshot({connectionGeneration, minStateRevision: ready.stateRevision})`；
3. 返回答复先核对 `connectionGeneration`，再核对 `sourceEpoch` 与单调 `stateRevision`；旧代际答复丢弃；
4. 收到 `committed／refreshed` 且 `stateRevision` 高于本地 → 重新 `snapshot`，直到覆盖；通知只是失效信号，不是内容来源；
5. `ready.sourceEpoch` 与本地描述符不同，或收到 `source-replaced` → 关闭旧流、按新描述符重新订阅并完整回读；代际大小不作比较；
6. 断线 → 重建流并完整回读，不沿用旧答复。

## 关键决定

1. **`unsynced` 与 `snapshot` 分开**：追不上已知修订时给“没有内容”的明确结论，比给一份修订对不上的树更安全；`source-drift` 则相反——磁盘内容本身是同一版，缺的只是“本机已接纳”这一步，所以给内容 + 显式未同步标记。
2. **通知不含内容**：失效流只在进程内传播修订号，内容一律回读，避免第二条内容来源与草稿冲突。
3. **代际与修订分开判断**：`sourceEpoch` 是替换边界，不做大小比较；`stateRevision` 只在同代际内单调。
4. **未决发布不算“已保存”**：读到 `prepared／publishing` 即重读，耗尽则 `unsynced(pending-operation)`。
5. **快照只读**：读取路径不写资料、不写聚合、不写隔离标记（聚合不可读时直接 `unknown-state` 拒绝，隔离由命令路径负责）。
