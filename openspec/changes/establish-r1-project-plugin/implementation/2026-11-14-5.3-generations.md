## 守卫顺序（每次读取）

1. **连接代际**：`答复.generation !== 当前 generation` → 丢弃（`stale-generation`）。重连时 `generation + 1`。
2. **源代际**：`sourceEpoch` 更小 → 整份丢弃（`stale-source`）；更大 → **替换边界**，接受内容且不与旧代际比较修订（`sourceEpoch` 大小无意义）。
3. **修订**：同代际内 `stateRevision` 更小 → 丢弃（`stale-revision`）；相等或更大 → 应用。
4. `unsynced` → 不改树，只在连接提示里说明未同步（宁显示旧内容并标未同步，也不混两版）。

## 草稿分离

- 草稿只由用户编辑产生，仅“保存成功”或“放弃草稿”清空；重连、轮询、源代际替换、快照刷新都不清空。
- 草稿保留进入时的 `planVersion／planRevision／sourceEpoch`；代数落后时 `isDraftBaselineStale()` 为真，面板提示“保存可能被拒绝（冲突时草稿保留）”。
- 保存失败／冲突／待核对／传输异常一律保留草稿且不标已保存（5.2 规则不变）；提交后回读同样受上面三层守卫约束，旧回执触发的读取不会把树退回旧版。

## 与 5.1 协议的关系

5.1 的“先订阅再回读”在 Client 侧尚未接线：当前是**轮询**（5 秒一次，带 `minStateRevision` 追读）。它保证不丢新状态（单调守卫），但不提供推送，也不具备宿主水位（`ready.stateRevision`）。接入 `follow` 后，轮询可退化为兜底。

## 实测证据

### 自动化（184/184）

| 测试 | 断言重点 |
|---|---|
| 旧连接 | 换代后旧代际答复（修订更高）返回 `stale-generation`，不覆盖当前快照 |
| 源代际 | 旧源（epoch 更小、修订更大）整份丢弃；新源（epoch 更大、修订 0）被接受 |
| 乱序快照 | 同代际内更小修订 `stale-revision` 不覆盖；更大修订应用 |
| 旧回执 | 提交后迟到的更旧快照不降级，`isSaved()` 仍为真 |
| 草稿跨重连／轮询 | 重连与轮询都不清草稿；换代后 `isDraftBaselineStale()` 为真 |
| 断线 | 轮询抛错 → `offline` 且树保留；`reconnect()` 代际 +1、状态回 `connected`、完整回读 |
| 轮询恢复 | 新修订被应用，离线提示清空 |

## 关键决定

1. **轮询而不是假装订阅**：宿主 `follow` 流需要 mux 与生成代理接线，本轮以轮询 + 单调守卫实现“不丢新状态”的实质要求，并在记录里标明协议缺口，不把轮询说成订阅。
2. **代际先于内容**：先判代际再判修订；旧代际答复即使修订更高也不采纳——重连后的世界已换代。
3. **换代不比较修订**：`sourceEpoch` 大小无意义，只作替换边界；否则“刷新后修订更小”会被误判为旧数据。
4. **草稿优先于权威**：刷新不清草稿是硬规则；基线过期只提示，不自动清空、不自动合并。
5. **未同步不改树**：`unsynced` 时保留旧内容 + 明确提示，比给一份混合版本安全。

## 未覆盖（不得当作通过）

- **订阅流**：`conaProject.follow` 未暴露；无推送、无 ready 水位，轮询间隔内的变化靠下次回读发现。
- **宿主重启**：外壳白屏需整页重载；草稿不持久化，重载即丢（R1 边界）。
- **票据级回执展示**：旧回执对“操作历史”的影响未做 UI（历史回执不替换当前树只测了数据层）。
- **多实例**：R1 单实例；跨实例不比较计数器（当前只有一个实例，未实测）。
- **E 层**：Agent 编辑同树仍属第 6 段。
