## 关键决定

1. **两套入口判据，不共用“owner 或为空即放行”**。`remote-owner` 由适配器在真实 owner invocation 上判定；`agent-work` 要求真实 `workRunId`、正数绑定版本且 `instanceId` 一致。缺上下文直接 `forbidden`，不降级为进程内 owner。
2. **提交前必重读**。命令自报的规划内容不作输入：先读注册表 → 核对实例与项目 id → 源代际 → 双修订 → `readSourceBaseline` 重读磁盘并核对 `planVersion`，之后才变换。
3. **先正文后头，头未知即待核对**。记录命令先写内容寻址正文（失败不发布头）；资料头 `unknown` 返回 `pending-reconciliation` 且**不推进修订**，避免把可能已发布的事实记成未提交。
4. **修订语义**：规划命令 `planRevision +1` 且 `stateRevision +1`；记录命令仅 `stateRevision +1`，`planVersion` 不变——因此记录之后仍可用原规划基线提交规划修改。
5. **队列不重试**。并发命令中只有基线成立的那条成功，其余 `plan-conflict`；不自动重放、不换 id，这是 4.2 幂等与 4.4 恢复的前提而不是替代。
6. **命令不带新节点 id**。`add-nodes`／`split-node` 只描述结构，id 由应用层生成，避免用模型指定身份覆盖旧节点。

8 项测试：

| 测试 | 断言重点 |
|---|---|
| 规划命令提交 | `impact=plan`、`planRevision=1`、`stateRevision=1`、磁盘节点 +1、聚合 `lastObservation` 与返回一致 |
| UI／工具同规则 | 两入口都成功；同一过期基线两入口都 `plan-conflict`；缺上下文／空 `workRunId`／实例不符都 `forbidden` |
| 过程记录 | `impact=state`、`planRevision` 不变、`planVersion` 不变、正文哈希与索引一致；随后用**原**规划基线提交规划成功且不丢记录 |
| 真实规划冲突 | 伪造 `expectedPlanVersion` 与过期 `expectedPlanRevision` 都 `plan-conflict`，文件字节不变 |
| 完成命令条件 | 无完成条件 → `invalid-project`；有条件但无验证记录仍拒绝；追加 `verification` 记录后 `done` 成功 |
| 源代际／身份 | 过期 `sourceEpoch` → `source-changed`；项目 id 不符 → `forbidden`；未知实例 → `binding-expired` |
| 并发队列 | 5 条同基线并发：1 条 committed、4 条 `plan-conflict`，磁盘只多一个节点且结构合法 |
| 发布失败结局 | 正文写入前注入失败 → `persistence-failed` 且头未发布；头 rename 后注入 → `pending-reconciliation(stage=head)` 且保留 operationId |
