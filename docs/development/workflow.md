# Change 编写、双审、提交与执行工作流

2026-11-12 用户明确约定；2026-11-13 用户增补：新建 change 采用双审，执行角色与作者/审阅分离。本文件记录当前有效流程，适用于本仓新建或继续编写的 OpenSpec change。

## 角色

| 角色 | 职责 | 约束 |
|---|---|---|
| 作者 | 编写 change、自检、按 review 修订 | 不审自己的 change；不预填 review，不以自查冒充外部审阅 |
| 审 1（DSH 侧） | 独立上下文审阅 change | 作者是 DSH 时改用独立 DSH 子会话，并在 review 中如实标注“同模型独立上下文”；只读，不实施 |
| 审 2（另一个 Agent） | 独立模型审阅 change | 与审 1 独立给结论；只读，不实施 |
| 执行 | 按 tasks 实施、回写证据 | 默认不与作者同一角色（常在 flash 级模型上执行），具体由用户按 change 选定；审阅者不执行 |

## 新建 change：编写 + 双审

1. 作者完成所用 schema 要求的 change 工件（R1 为 proposal、design、增量 specs 和 tasks），核对范围、依赖及可验收场景，并运行 OpenSpec 严格校验与仓库门禁。
2. **写完 change 后不立即 Git 提交。** 保留工作区中的完整提案，将 change 路径、校验结果和已知待核查项交给用户，由用户安排双审；提案编写任务不自动扩展为产品实施。
3. 审 1 在该 change 目录的 `review.md` 中追加 `## 审 1 · DSH · <日期>` 节，记录审阅范围、问题、依据及结论（放行／有条件放行／拒绝）。
4. 审 2 追加 `## 审 2 · <Agent/模型> · <日期>` 节，独立给出结论。两位审阅者都可读原始 change，但不共享结论、不代填对方意见。
5. 作者完整阅读两份 review，按问题的实际影响修订 proposal、design、specs 和 tasks；对不采纳或延期的意见在 `review-response.md` 记录理由及位置。两位意见冲突或涉及目标/范围取舍时交用户裁决，不由作者自行选边。
6. 双审确认（或用户裁决）后重新运行校验和仓库门禁，再 Git 提交。只有一份 review 时保持待审阅、不提交。

`review.md` 与 `review-response.md` 是 change 内的约定文件名，属于文档命名规则的固定文件例外。复审时在同一 review 中追加清楚的轮次、审阅者与范围，并同步响应；实质性新增问题不能被旧结论掩盖。

## 建立后的修订

- change 提交后的一般修订（任务拆分、措辞、局部设计调整）不强制双审，至少 1 名非作者审阅；微小修（错字、链接、单行、格式）作者自检即可，并在 `review-response.md` 记一笔。
- 涉及验收范围或目标变更的修订，建议回到原审阅者确认；修订触发事实、变更清单与依据写入 change（如新增 amendment 文档），不直接改任务勾选。
- 实施中发现验收前提错误时，先修订 change 再继续；不得为了让已完成工作通过而放宽标准。

## 执行与验收

- change 提交只表示经审阅的提案已保存，不等于实现、验收或归档；实施遵循用户实际授权。
- 执行 Agent 由用户按 change 选定，默认不与作者同一角色；审阅者不承担执行。
- 执行按 tasks 记录产品实现与验证；证据写回环境记录与验证矩阵，tasks 只在有实际运行证据时勾选，未测/受阻保持 `untested`／`blocked`。
- 范围或验收变化按上一节修订 change，不直接改勾选状态。

## 状态与验证

- OpenSpec 的工件齐备或校验通过不代表外部审阅已完成；没有 `review.md` 或双审未齐时仍处于待审阅状态，不自动提交。
- 提案中的验收场景在真正执行前保持 `untested`；运行结论只使用 `pass` / `fail` / `blocked` / `untested`，替身通过不代替真实宿主。
- 校验至少包括所用 OpenSpec 版本的 change 严格校验和 `node scripts/check-repo.mjs --all`；插件实现后再加入实际构建、类型及必要测试。
- 在 change 的交接／review-response 中保存校验工具准确版本、命令、输出摘要和环境边界。复查使用明确版本，不用 latest 结果冒充编写时版本；其他版本的补跑分别归属。门禁只读取 Git 索引时，新增工件须暂存后检查或用包含新文件的独立快照检查，并写明范围。
- push 与 tag 仍须用户明确指示，不因允许 Git 提交而自动获得授权。
