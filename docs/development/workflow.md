# Change 编写、审阅与提交工作流

2026-11-12 用户明确约定。本文件记录当前有效流程；适用于本仓新建或继续编写的 OpenSpec change。

## 编写与交接

1. 编写 Agent 完成所用 schema 要求的 change 工件（R1 为 proposal、design、增量 specs 和 tasks），核对范围、依赖及可验收场景，并运行 OpenSpec 校验与仓库门禁。
2. **写完 change 后不立即 Git 提交。** 保留工作区中的完整提案，将 change 路径、校验结果和已知待核查项交给用户，由用户安排其他 Agent 审阅；提案编写任务不自动扩展为产品实施。
3. 审阅 Agent 在该 change 目录中写入 `review.md`，记录审阅范围、问题、依据及建议。此文件由实际审阅产生，编写 Agent 不预建空白文件，也不以自查冒充外部审阅。
4. 编写 Agent 收到审阅完成的交接后，先完整阅读 `review.md`，按问题的实际影响修订 proposal、design、specs 和 tasks；对不采纳或延期的意见记录理由，不能只因存在评审文件就视为问题已处理。
5. 在 `review-response.md` 中逐项记录处理情况及对应位置，保留原始 `review.md`。仍影响目标、契约或实施可行性的问题须解决或明确交回用户处理，不能带着未说明的阻塞项提交。
6. 修订后重新运行相关校验和仓库门禁，再进行 Git 提交。提交只表示经过审阅修订的提案已保存，不等于功能实现、验收或 change 归档；实施遵循用户实际授权，已有明确实施授权继续有效，不要求重复批准。

`review.md` 与 `review-response.md` 是 change 内的约定文件名，属于文档命名规则的固定文件例外。复审时在同一 review 中追加清楚的轮次／范围，并同步响应；实质性新增问题不能被旧结论掩盖。

## 状态与验证

- OpenSpec 的工件齐备或校验通过不代表外部审阅已完成；没有 `review.md` 时仍处于待审阅状态，不自动提交。
- tasks 记录产品实现与验证工作，编写提案本身不勾选实现任务。评审、提案提交与归档流程另列说明，避免误算实现进度。
- 运行结论只使用 `pass` / `fail` / `blocked` / `untested`；提案中的验收场景在真正执行前保持 `untested`。
- 校验至少包括所用 OpenSpec 版本的 change 严格校验和 `node scripts/check-repo.mjs --all`；插件实现后再加入实际构建、类型及必要测试。
- 在 change 的交接／review-response 中保存校验工具准确版本、命令、输出摘要和环境边界。复查使用明确版本，不用 latest 结果冒充编写时版本；其他版本的补跑分别归属。门禁只读取 Git 索引时，新增工件须暂存后检查或用包含新文件的独立快照检查，并写明范围。
- push 与 tag 仍须用户明确指示，不因允许 Git 提交而自动获得授权。
