## 设计起点

用户在本次讨论中明确：以 DSH 为 Agent 底座，围绕项目规划扩展能力，精简旧 Cona 完整应用设计。2026-11-11 进一步澄清：主要使用场景是项目代码开发，视频制作只是偶尔出现的需求。默认使用过程、流程模板与验证案例应围绕代码开发及相关文档工作设计；视频等工作仍可按需加入项目，不将其提升为与代码开发并列的主要场景。文件回溯不作为本次架构的驱动力。

以下需求已由用户明确提出：

- 预设流程与用户自建流程可以作为起点，项目和大阶段都能继续拆出子阶段。
- 项目骨架既可在项目开始时应用，也可在后续阶段加入；来源可以是预设，或由 Agent 从用户已有项目提炼的模板。
- Agent 应能根据新内容与信息，自主调整较大或较小的项目阶段。
- 阶段与对话为多对多：一个阶段关联多个对话，一个对话也可关联多个阶段。
- 考虑 DSH 官方未来可能加入 Super-agent 能力，提前准备项目规划数据与接入边界；本轮不以自研 Super-agent 或多 Agent 调度系统为目标。
- 代码开发通常采用 OpenSpec 一类的 SDD 范式；项目工具可以在变更影响足够大时提醒建立或更新 spec、change 和验证记录。简单任务不需要强行创建完整规范流程。
- SDD 提醒须提供开关，尊重用户是否启用的选择；关闭后不主动提醒，也不因发现 OpenSpec 目录或任务变复杂而自动重新开启。默认值和设置范围尚未确定。
- 从零开发包含调研、竞品对照等立项工作；已有项目提供专门聊天进行项目分析，项目进行中也可再次分析，评估是否需要调整。
- 项目树颗粒度先采用 Agent 提出的默认方案，探索与实施的具体边界也通过使用优化。先形成完整架构，减少用户逐项决定的负担，不将当前建议当作不可修改的定论。
- 项目界面与功能集成在 DSH 软件内；项目面板属于 DSH 界面，Host 项目服务属于 DSH 宿主插件逻辑，不要求另开网站、独立应用或单独部署后端。
- 用户可以直接编辑项目树中的阶段，像搭积木一样搭建和拼接流程；具体操作方式先按下述设计实现验证，再通过使用优化。
- 项目树、目标路线图和时间路线图共用一份规划，时间可逐步补充，依赖、展示顺序与日期分别表达；用户已认可整体设计。
- 插件支持 i18n，首版完整支持简体中文与英文，其他宿主语言回退英文；这是用户明确选择的语言范围。
- 多人可以使用不同开发环境及不同 Agent；项目资料保留非 DSH Agent 可读性，新机器 DSH 取得资料后可继续接入。
- 按项目选择资料放在项目目录并可用 Git 管理，或放在 DSH／自定义目录，不强制用户采用唯一位置。

下文的数据划分、调整规则与实施顺序均为设计建议，仍可讨论，不将其写成用户已逐项确认的决定。

## 项目资料与跨环境协作

建议三种位置使用同一套带版本的公开 JSON／Markdown 资料格式和阅读入口，记录规划、决定、选定的分析摘要、成果与接续说明。其他 Agent 可直接读取并按协议修改，新机器 DSH 校验后沿用项目／节点身份，重新建立本机目录及聊天关联。

机器绝对路径、实际 Session、活动授权和私有回执留在本机，不自动随 Git 发布。用户决定哪些资料共享，插件保存不自动提交或同步 Git。分支合并后重新做领域校验，冲突不被旧缓存覆盖；具体恢复、格式和迁移见[数据可移植草案](../architecture/2026-11-12-project-data-portability.md)，不将文件协作描述成实时多写者调度能力。

## 使用过程基线

### 从零开始

用户描述想做的产品，Agent 按需要组织需求调研、竞品对照、技术可行性和范围收敛。用户可以补充材料或沿用已有结论；阶段允许反复，不把所有项目强制套进相同的商业立项流程。研究结果区分来源事实、推断和未核查项，再形成初始目标、近期规划与骨架建议。

立项讨论可以先建立逻辑项目，不要求用户先准备完整仓库。需要实际开发时再按所选骨架准备目录、关联 DSH Workspace，并进入开发流程。文件创建与规划创建分别记录，避免把计划中的结构展示成已生成代码。

### 接入已有项目与再次分析

关联现有工作目录后，用户可发起专门的项目分析聊天，分析代码、文档、已有 spec／change、当前规划和实际验证记录，形成有来源的项目现状、缺口与调整建议。范围与读取覆盖情况可查，静态分析不冒充运行验证。

同一入口也用于项目进行中的复盘或局部分析。分析结束不自动重写代码或推翻目标；先保存发现，再在当前请求与既有授权范围内应用规划。分析过程中发生的新变化需重新核对，过时分析不能直接覆盖新状态。

### 日常开发与接续

默认树按“项目 → 里程碑／版本目标 → 功能／问题 → 必要的子工作”组织，允许省略层次；远期粗、近期细。关联 OpenSpec tasks 时优先展示工件中的清单，不维护一份必须重复勾选的任务状态。

用户在 DSH 内通过聊天探索想法、分析问题或开始实施。系统展示当前工作对象和意图，依据明确表达和既有授权推进；模糊时先做独立阅读，仅在依赖用户选择时集中澄清。点击另一节点只改变浏览，不能悄悄改变执行目标。

一个功能可关联需求、实现、排错和评审等多次聊天，新聊天获得相关目标、决定、规范、成果和未解决问题的有来源摘要。临时插单保留原工作的接续信息。结束时呈现真实成果和验证状态，返回项目概览后能看清当前目标、阻塞、需要决定的事和建议下一步。

上述默认流程、上下文规则、状态与实践验证顺序见[架构草案](../architecture/2026-11-11-project-development-architecture.md)，当前没有运行证据。

## 1. 代码开发与 SDD 工作流

项目管理树回答“要做什么、为什么做、先后如何安排”，SDD 工件回答“行为如何定义、如何实现、如何验证”。两者应相互关联，但不把每个树节点都变成一份规范。

建议将 OpenSpec 作为首个 SDD 工作流适配器，而不是把项目模型绑定到 OpenSpec 的目录格式。项目节点可以关联一个或多个 change、spec、设计记录、任务清单和验证证据；一个 change 也可以覆盖多个节点。未来接入其他 SDD 工具时，复用同一组项目关系与状态，替换工件适配层。

SDD 提醒提供明确的启用／关闭设置；关闭后不在聊天、通知或节点提示中主动催促采用 SDD。用户仍可主动要求读取、建立或更新 spec／change，已有工件关联与状态也可继续查看。开关控制插件附加提醒，不修改仓库已有的开发规则、验证要求或门禁。

建议提供个人默认设置，并允许按项目覆盖，以适应不同项目的工作方式；当前默认值、设置范围与生效时机待讨论，不预设已获用户确认。提醒偏好应持久保存并供 UI 与 Agent 共用，新聊天或任务范围扩大不应丢失已关闭的选择。

提醒启用时，Agent 可按变更影响建议工作方式：

| 变更级别 | 典型情况 | 建议行为 |
|---|---|---|
| 简单任务 | 拼写、内部局部重命名、恢复已有规范行为的小修复 | 按项目约定直接执行并做适当验证，不强制新建 spec 或完整 change |
| 有边界的功能变化 | 新增一个用户可见行为、修改已有接口约束、改变一段已有能力的完成条件 | 提醒检查现有 spec；没有覆盖时建立轻量 change 或补充规范，再实现和验证 |
| 跨模块或架构变化 | 新能力、数据模型变化、跨包协议、权限或生命周期变化 | 建议先建立完整 change，明确 proposal／design／spec 场景／tasks，再开始实现 |

上述分级及具体触发方式仍为建议。判断应依据行为、兼容性、风险与不确定性，不能仅按文件数量或节点大小决定；小范围的权限修复也可能需要完整流程。项目已有 SDD 规则时优先遵循其约定；额外的提醒不自动成为实施阻断，也不能绕过项目现有门禁。用户明确跳过可选提醒后，同一事项不要重复催促；范围扩大或实现与已有规范冲突时再说明新情况。

在用户启用 SDD 提醒或主动选择该流程时，一个典型代码功能可以这样推进：

1. 用户提出“增加登录方式”，Agent 检查项目树、现有 spec、未完成 change 和相关聊天，判断这不是简单任务。
2. Agent 建议建立或继续一个 change，先整理目标、非目标、影响的现有行为和可验收场景，再按项目工作流拆出实现任务；需要澄清产品行为时集中请用户决定。
3. 实现过程中，代码、测试和讨论都关联到该 change 与对应阶段。发现需要修改令牌生命周期时，Agent 提示更新 spec 和依赖，而不是静默扩大任务范围。
4. 完成前，Agent 对照 spec 场景、测试结果和人工验收状态，区分已验证、未测、失败和受阻；“代码已写完”不自动等于功能完成。
5. 变更稳定后，按 OpenSpec 工作流归档或关闭 change，并把最终 spec、成果和验证证据留在项目记录中。后续新需求建立新的 change，保留前一版本的决策和历史。

建议结合项目工作流和实际工件状态生成提醒。可记录关联工件及其版本、验证状态、必要的跳过说明，供 UI 与模型工具共同读取；具体字段与检查机制待验证。项目界面展示仓库中的 spec／change 状态与引用，不另存一份可独立编辑的规范正文。手工修改、移动、归档工件后应重新核对关联；文件存在或 tasks 已勾选都不能单独证明规范已满足。

## 2. 动态项目树

流程模板产生初始结构。实际项目的树可以随目标澄清、材料补充、实验结果和工作反馈演化。

### 用户直接搭建与调整

DSH 内的项目树同时是用户可操作的规划编辑器。用户可以直接修改阶段名称、目标和完成条件，也可以通过拖动、插入和组合调整结构，无需先要求 Agent 代为修改。

建议将一个阶段及其子阶段作为可组合的单元，支持：

- 新建空白阶段，或从流程模板选择一段子树插入指定位置。
- 拖动整个阶段调整顺序，或移入／移出其他阶段；提供等价的菜单与键盘操作。
- 把选中的阶段包成一个大阶段，继续拆分、合并或替换；复杂调整先展示结果再提交。
- 复制阶段结构、保存为可复用流程模板，并在后续节点再次应用。
- 撤销／重做规划编辑，保留历史，遇到其他修改时核对冲突。

拖动位置表达归属和展示顺序，执行先后通过独立依赖关系表达。移动保留节点身份、成果与聊天关联；复制产生新的身份，默认只复制目标和结构，不继承已完成状态、执行历史或授权。阶段改名／移动不直接改写代码目录、OpenSpec 正文或已运行任务。

用户编辑与 Agent 调整都经同一项目服务检查并提交，手工变更是后续规划依据；Agent 不因仍持有旧规划就把用户的修改改回去。影响正在执行的目标或必要依赖时，显示受影响工作并确定接续方式；普通结构调整无需逐次弹窗。

建议将新信息处理成如下过程：

> 记录来源与事实 → 判断影响哪些节点 → 形成具体规划变更 → 核对当前规划与授权 → 提交变更 → 更新相关工作。

Agent 可提出或执行新增、拆分、重排、合并、替换、取消与重新打开节点。取消和替换保留原节点身份及历史，不抹去已经发生的讨论、成果或完成依据。

自主程度应依据实际影响和用户授权判断，不能仅按节点大小决定。一个大阶段在既定目标内重组，也可以属于允许的自动规划；一个小任务若扩大目标、改变已确认交付或引入新的费用与外部动作，也可能需要用户决定。具体默认策略待定，不把每次树调整都变成人工审批。

自动变更记录简短原因、触发信息和前后结构。只有影响目标、依赖、可行性或完成条件的信息才需要调整规划，避免每条消息都生成节点。相关变化尽量合并展示。

正在执行的工作绑定当时的目标与规划修订。重排树不能静默改变其执行目标：可不受影响地继续、追加说明、等待边界或停止重派，具体由变更影响决定。陈旧规划生成的变更不能直接覆盖新规划。

## 3. 树与关系

树表达工作归属。节点可表示大阶段、子阶段或具体工作，允许混合内容；标签与执行方式不限制子节点类型。

依赖、共享材料及关联对话分别记录，不挤进树的父子关系。一个节点需要在多处展示时，可通过引用呈现同一节点，不复制出多份独立状态。

节点数量和子节点完成率提供进展线索，但不能单独证明父阶段完成；阶段还需要自己的成果与完成条件。

## 4. 阶段与对话的多对多关联

建议将三种关系分别管理：

| 关系 | 回答的问题 |
|---|---|
| 节点与对话的关联 | 哪些讨论、执行或审阅与该节点有关 |
| 上下文引用或订阅 | 哪些新信息应提供给哪些规划者或执行者 |
| 工作执行记录 | 哪个 Agent 在哪次执行中，为哪些节点做了什么，结果是什么 |

因此，不在节点上用唯一 `sessionId` 表达全部工作，也不让某个全局“当前节点”支配所有会话。

一次接口设计讨论可以同时关联前端页面与后端接口节点；一个功能节点可以关联需求讨论、代码实现、测试和评审等多个对话。偶尔需要制作演示视频时，也可在项目中增加相应节点并关联制作与审阅聊天。后续可把关联细化到相关消息区间，避免把整段聊天都当成每个节点的背景。

关联本身不意味着持续同步全部内容，也不意味着该对话可以修改所有关联阶段。新信息应按关联用途和影响范围分发。必要时引用相关片段、阶段结论和成果，完整历史按需读取。

DSH 已有的会话引用是有界只读快照，不是长期实时订阅；其单条消息最多引用三个来源的限制，也不应被误用为项目只能关联三个对话。

## 5. 为官方后续能力准备接入边界

建议在项目规划与执行之间保留可替换的接入层。一个节点可以由普通会话、多个执行会话、subagent、Workflow 或未来其他执行方式完成。节点不绑定某一种执行器的生命周期。

当前先让用户正在使用的普通 DSH Agent，通过项目工具读取目标、获取相关信息、调整阶段并提交成果。这已经能验证自主规划，不必先建立另一套常驻协调 Agent。

为未来官方 Super-agent 准备的重点是稳定的项目身份、项目／节点与会话的多对多关系、带修订与来源的项目操作，以及可查询的成果和执行记录。后续官方能力可通过适配调用同一项目服务，继续使用既有项目数据。

官方尚未发布的协议不提前当成事实，也不为假想协议实现空适配器或通用调度框架。先验证当前 DSH 可用的工具、上下文与会话接口，待官方接口明确后再做具体映射；如果官方将来也提供项目领域能力，再评估哪些部分复用、迁移或保留。

接入后的规划协调角色可以负责新信息研判、阶段拆分与依赖调整、工作分配，以及集中提出必要决定；该职责由谁实现仍保持开放，不由插件预先固定为自研服务。

执行者围绕明确的目标、节点集合、输入与规划修订工作，提交成果或结构化状态。一个节点可有多次执行，一次执行也可服务多个节点。换会话、重试、停止及接续都不重新创建项目节点来代替历史记录。

多个 Agent 通过同一项目服务读写规划。需要记录更新依据并检查修订，避免各自依据旧树反复拆分、覆盖或重复派工。

## 6. Super-agent 调研与可借鉴部分

已找到官方仓库 [deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)。本次读取的完整小型源码快照提交为 `8c32a9dc5d72c033816c6a8110b37f40cf94fba4`，归档约 687 KiB，仅用于静态调研，未安装或运行。

README 引用技术文章 *Exploring Super-agent Design: Towards a More Autonomous Agent System*，同时明确：这是供参考的研究原型，不是正式产品；公开实现与文章不完全一致，部分文章方向尚未实现。本次已核查原型文档和部分源码，不宣称已核实文章全部内容。

与本项目直接相关的设计包括：

- **事件驱动研判**：Source 产生 Trigger，评估后决定是否创建工作或继续既有工作。
- **多对多订阅**：Ticket 与 Thread 通过 Subscription 关联，对话可以承载多个工作项；关联背景与授权分别判断。
- **独立派工**：Assignment 把工作项绑定到执行者，工作项不跟随执行会话直接结束；可接续、换派或重新执行。
- **减少人工注意力开销**：按请求或已允许规则行动，集中呈现需要人处理的事项和有用结果。

可以借鉴上述职责与关系。原型面向一个 GitHub 仓库，并可接入飞书；它没有直接提供本项目需要的多层项目树、跨类型创作流程与骨架模板，也不能把每个 Ticket 直接视为我们的一个阶段。

DSH 本身已有可继续的 subagent（rc.2 起支持具名与多层协作）、一次性 Workflow，以及按会话开启的 Agent Team。Team 在 rc.2 中已从 `packages/experimental/` 迁至 `packages/team/`，为开启该模式的会话树提供持久化共享任务板，成员共享同一检出目录；它不创建隔离工作目录、不跨进程协调，也不提供文件写锁，更不能承载跨会话的项目状态。项目不应直接等同于一个 Team。这属于宿主执行侧能力，不改变「本轮不自研 Super-agent 或多 Agent 调度系统」的边界。

该原型用于理解未来能力的可能边界，不能证明 DSH 已承诺正式集成的时间或最终接口。本轮不移植其执行与调度系统，也不绑定其 GitHub／飞书渠道、目录规则和部署权限。对外发布与消息发送需在后续明确场景下单独设计。

## 7. 建议的验证顺序

第一段闭环就包含自主规划，而不是只做手工树后再考虑它：

1. 用模板或讨论建立一棵项目树，保存身份、结构和规划修订。
2. 多对多关联节点与聊天，并在当前执行中明确目标节点。
3. 向 Agent 提供新材料，在已允许范围内自动修改阶段结构，界面展示原因和变化。
4. 由用户或执行者提交成果与状态，冲突时保留事实并重新核对。
5. 核查前述接口与数据没有绑定一个会话或某种执行器，为后续官方协调能力接入保留替换空间。

底层从开始就容纳多对多关系和多次执行。官方 Super-agent、自动并行、后台监听和外部渠道不作为上述最小闭环的前置实现；后续按宿主实际发布能力与使用需要逐步接入。

当前没有上述闭环的运行证据，验证状态均为 `untested`。DSH 接口依据见[项目管理插件接入调研](../research/2026-11-11-dsh-project-management-review.md)。
