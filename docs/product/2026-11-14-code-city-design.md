# 每日代码城市讨论草案

日期：2026-11-14。状态：用户提出以每日代码行数生成 3D 城市，为代码开发增加情绪价值，明确选择“每天一个街区，长期累积成城”，并选择按 Git 提交统计，以便老项目接入时也能利用历史记录形成城市。统计细则、视觉映射、数据保存和交付范围尚未确定；没有实现与运行验证，不修改当前 R1 验收或开发排期。

## 用户想要的体验

每天的代码开发留下一个可回看的街区，日积月累形成一座城市。用户能看到自己持续建设项目的痕迹，获得轻松的满足感。功能集成在 DSH 项目界面内，沿用[项目管理方向](2026-11-11-project-management-design.md)。

用户明确的内容：

- 按自然日记录代码行数，覆盖当天 00:00 到当天 24:00。
- 把代码量转成有 3D 城市感觉的视觉内容，提供情绪价值。
- 每天生成一个街区，多个街区长期累积成城。
- 按 Git 提交中的新增／删除行数统计；已有项目接入时可回读历史提交，生成过去的街区，不必从安装插件当天开始积累。

下文均为设计建议，用户尚未逐项确认。

## 一天如何呈现

用户已明确项目入口放在 DSH 整个窗口顶部，点击向下展开项目面板，见[项目入口与面板](2026-11-11-project-management-design.md#项目入口与面板)。建议在展开面板的项目概览中放一个城市预览；完整城市可使用更大的视图，具体是在面板内放大还是进入项目主视图待讨论。城市打开后可旋转、缩放，并按日期定位街区。当日街区随已统计的活动更新，跨日后保留历史；点击街区查看日期、新增／删除行数、统计来源和覆盖情况。

可先尝试低多边形或等距视角：一天是一个街区，文件或模块是建筑，建筑数量、层数及灯光表达当天的代码变化。采用有上限的分档或非线性缩放，让几十行的小修也能形成可辨认的街区，避免大批生成代码把画面挤满。布局与配色依据稳定身份生成，刷新后保留位置；后续设计规则变化时说明是否重绘历史。

例如，一天新增 180 行、删除 120 行，可以出现几栋建筑及翻新景观，详情同时显示这两个数。用 `180 - 120 = 60` 作为唯一成长值会掩盖重构活动，建议避免。删除如何映射为翻新、绿地或其他景观，留待视觉原型比较。

休息日可以保留安静的空地、街景或日期位置；不因没有代码而让已有建筑衰败，也不加入断签惩罚。代码量只表达活动痕迹，项目节点完成、质量与验证继续读取现有成果记录。讨论、调研和评审当天即使没有代码，也可以是有价值的一天。

## 自然日与统计口径

“当天 24:00”按次日 00:00 理解，区间为 `[当天 00:00, 次日 00:00)`，边界事件只归属一天。建议明确一个统计时区并保存，界面语言或机器时区变化不静默重分历史。遇到夏令时，自然日可能是 23 或 25 小时；严格滚动 24 小时与自然日是不同口径，本设想先按用户描述讨论自然日。

用户已选择 Git 提交口径，界面明确标注“当日提交变更行数”。历史提交与接入后的新提交使用相同统计规则；未提交修改不计入，提交日期不能解释为实际编辑日期。

下面保留不同口径的比较作为设计依据；文件基线与连续变更采集不纳入当前选定方案：

| 候选口径 | 能呈现的活动 | 局限 |
|---|---|---|
| Git 提交中的新增／删除行数 | 可回读历史，不要求 DSH 全天运行；可保留提交来源 | 归到提交日期，无法还原实际编辑日期；多次提交可能重复改同一行，合并、变基和跨分支须去重 |
| 当天文件基线与当前内容的差异 | 包含未提交代码，贴近当天保留下来的修改 | 需要可用的日界基线；改完又撤销的过程不可见；关闭 DSH 时无法连续观测 |
| 连续记录文件变更 | 能表现当天反复编辑的活动 | 保存、格式化、分支切换会放大量；采集成本与数据量更高，遗漏期间无法精确补全 |

后续仍需确定提交范围、采用作者时间还是提交者时间，以及合并与历史改写的处理方式。多次提交修改同一行属于多次变更，不把变更行数描述为互不重复的源码行数。

不要求午夜常驻任务：可在打开城市时回读本地可用历史，按日期补算街区。已有项目首次接入即可形成历史城市，不要求插件曾在过去运行；浅克隆或历史不完整时说明覆盖范围，不把缺失历史显示为“0 行”，也不自动下载缺失历史。没有 Git 提交历史的项目显示尚无可统计记录。

## 代码范围与归属

建议初期按项目展示城市，统计相关仓库选定范围内的变更。是否需要个人跨项目总城、多人共同城市或个人贡献筛选，继续讨论，不自动将整个团队的代码称为“你写的代码”。

- 新增与删除分别保存；活动量可用新增加删除表达，但明确它不是独立代码行数或生产力分数。
- 默认候选范围为源码与测试；文档、配置是否加入，以及不同语言如何分类，提供清楚规则，继续讨论。
- 建议排除依赖、构建产物、锁文件、二进制与生成代码；允许项目调整范围，统计保留规则版本。
- 重命名、格式化、合并、变基、cherry-pick、多工作副本和多个机器会影响计数与去重；统计细则单独验证，不预先承诺准确还原所有开发活动。
- 人工与 Agent 共同开发难以凭 Git 作者或文件变化可靠区分。默认描述为“项目代码活动”，不推断个人手写行数。

## 接入与数据建议

城市属于活动展示，与项目树、路线图及完成条件分开；统计刷新不自动修改规划、推进工作状态或授予 Agent 新权限。仍保持 DSH 内部插件、纯 Node ESM 与跨平台边界。3D 可在 Client 内使用浏览器渲染，具体库、宿主兼容性和性能尚待原型验证；静态预览或二维替代可作为性能与可访问性方案。

采集建议只读取用户关联的仓库。首先考虑本机保存日期、时区、口径版本、聚合计数和核对所需来源，不为城市额外保存完整代码副本。Git 历史是可重建的统计来源；跨机器保持相同城市外观所需的规则、布局及设置，以及是否共享或导出城市资料，须遵循[资料位置与协作边界](../architecture/2026-11-12-project-data-portability.md)另行设计，不直接向当前 v1 公开格式加字段。

建议提供开关、减少动画设置和文字统计视图；隐藏面板时暂停渲染。分享城市图片可以作为后续想法，用户主动触发，并明确图片是否含项目名或文件信息。

## 下一步讨论与验证

视觉生长方式与 Git 提交口径已经由用户选定。后续细化城市按项目还是个人跨项目组织、提交日期及分支范围等规则。可以先使用模拟数据做一个可旋转、可选日期的视觉原型，检验是否带来预期的情绪价值，再用已有项目的历史提交验证首次接入效果与统计成本。

视觉原型不代表统计能力已实现。正式开发前另建 change，按[工作流](../development/workflow.md)审阅；日界时区、删除与重构、重复提交、浅克隆与缺失历史、历史重建、大仓库性能和关闭功能后的行为均需实际验证。目前均为 `untested`。
