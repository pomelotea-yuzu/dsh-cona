# 项目路线图功能讨论草案

日期：2026-11-12。状态：用户已认可项目树与路线图共用规划、结合目标与时间视角的整体设计；具体界面、时间精度和排期能力继续细化。尚未实现，运行验证为 `untested`。

## 讨论来源与问题

用户在要求 dsh-cona 自身有开发路线图后，进一步提出：插件本身就是项目规划工具，可以加入路线图功能。本轮明确希望先讨论“里程碑、交付成果与推进顺序”和“日期、工期与排期”如何结合，暂不选择侧重点。

后续用户明确“这个设计我是认可的”：本轮确认采用同一份规划支撑项目树、目标路线图与时间路线图，时间可逐步补充，展示、依赖与日期分别表达，并保留 Agent 调整的原因和成果依据。该认可不扩展为完整甘特图、自动排期或文中所有实现细节均已定稿。开发安排见[本项目路线图](../engineering/2026-11-12-plugin-development-roadmap.md)，既有项目模型与授权边界见[项目管理设计](2026-11-11-project-management-design.md)和[架构草案](../architecture/2026-11-11-project-development-architecture.md)。

## 一套规划，两种路线图视角

路线图与项目树共用目标、节点身份、依赖、完成条件和实际成果。详细项目树可以继续展开到工作项，路线图按当前需要选出里程碑、阶段或重要功能，并提供两个相互对应的视角：

| 视角 | 主要回答 | 呈现内容 |
|---|---|---|
| 目标视图 | 要交付什么，为什么先做它，现在卡在哪里 | 里程碑、成果与完成条件、关键依赖、实际进展、阻塞和下一步 |
| 时间视图 | 希望何时推进，时间是否冲突，改期影响哪些工作 | 同一批目标的可选时间窗口、已明确的日期约定、实际发生时间、依赖与时间冲突 |

用户可以先只列目标和依赖，逐步补充时间，也可以一开始就有交付日期；切换视图不创建另一份独立任务状态。没有排期的目标在时间视图中保留“未排期”位置，不能因缺少日期而隐藏或无法建项目。

选中路线图中的里程碑，可以展开对应工作、查看成果或打开关联聊天。多个视图引用同一个节点，节点改名、移动、取消或替换时保留身份与历史。路线图筛选和卡片布局属于展示设置，不直接改变树的父子结构。

2026-11-12 用户授权依据纸面评审修订后，首版设计采用：里程碑仍是带自身交付条件的 WorkNode，通过交付关联引用同项目不同分支的工作或成果。例如“首版可用”关联界面、存储和 Agent 联动，无需改变它们的树归属，也不复制路线图专用完成状态。

交付关联表达成果来源，执行依赖表达推进条件；引用不会自动生成执行依赖或递归推导完成。里程碑仍核对自身条件和实际证据。节点移动保留关联，取消、替换或引用失效提示核对，不按同名重新认领。具体字段和验证见[架构的跨分支里程碑方案](../architecture/2026-11-11-project-development-architecture.md#跨分支交付里程碑)，尚未运行验证。

## 用本项目检验两种视角

当前 dsh-cona 的开发路线图可以展示为以下内容，暂不编造日期：

| 路线图目标 | 交付依据 | 先后关系 | 时间安排 |
|---|---|---|---|
| R1：插件贯通 | 面板、持久数据、聊天、Agent 与 UI 实际联动 | 后续功能依赖接入验证 | 未排期 |
| R2：项目树与接续 | 用户搭建流程并与 Agent 共用规划，换聊天可继续 | 依赖 R1 | 未排期 |
| R3：分析与规划调整 | 已有项目分析和开发中复盘能留下来源并安全更新规划 | 依赖 R2 | 未排期 |
| R6：首版试用 | 对照开发路线图中明确的交付关口与完整试用结果 | 依赖 R1–R5 的交付与验证 | 未排期 |

目标视图直接显示这些交付关系。之后如果用户为首版填写目标日期，时间视图才增加时间位置；日期本身不证明排期可行，也不把工作标成已完成。把 R3 的卡片拖到 R2 前面，不能默默删除“R3 依赖 R2”。

路线图还应能表达“近期细化、远期粗略”：近期展开到功能或工作包，远期保留版本目标和主要依赖，避免 Agent 为了填满时间轴虚构所有工期。

## 时间信息如何加入

建议区分三种事实：用户希望的时间、已明确约定的截止条件，以及工作实际开始／完成的时间。期望日期的变动与违反明确约定有不同影响，实际发生时间须有执行记录或明确来源。

时间表达可以先允许宽窗口，例如某周或某月，再细化到日期。没有根据时保持未知；Agent 可以给出估计及其依据和不确定性，不能把自己的估计升级为用户承诺。目标日期临近也不自动启动执行或扩大权限。

第一轮交互试验需要核对：

1. 用户能否从交付视图为一个目标补充时间，并在时间视图看到同一目标。
2. 未排期、已排期、延期和受阻是否能被准确区分；时间经过不等于完成。
3. 修改日期后，是否能看清相关依赖及正在执行的工作受到什么影响。
4. 用户是否实际需要精确工期、日历和自动排期，还是粗粒度窗口已足够。

工时、工作日历、资源容量、关键路径和自动联动改期均会增加新的模型与规则，目前没有足够讨论把它们列为既定首版范围。先验证有日期与无日期目标共存，再决定这些能力的必要性。

## 编辑与 Agent 规划共用规则

路线图中的操作应明确区分以下影响：

| 操作 | 建议语义 |
|---|---|
| 调整卡片位置或筛选层级 | 改变展示，不自动修改依赖、日期或执行目标 |
| 修改目标或完成条件 | 经统一项目服务提交，核对修订，并记录对当前工作的影响 |
| 增删依赖 | 独立的规划变更，检查依赖环和受影响工作 |
| 修改时间窗口 | 明确记录期望或约定的变更，提示冲突；是否联动其他目标另行决定 |
| Agent 提出重排或改期 | 保存新信息、理由、影响与依据修订，在当前授权内提交；扩大范围或改变明确约定时集中提出选择 |

普通布局调整不应引发审批；已授权目标内的自主规划继续有效。路线图不能成为第二套授权系统，也不能把拖动日期解释为暂停任务、切换 Agent 或开始新工作。

UI、Agent 和项目树读取同一份已校验规划。跨环境基线使用规划内容指纹 `planVersion`，本机 `planRevision`／`stateRevision` 只在资料实例内排序，两个分支的自增计数不能比较新旧。分析或执行记录追加不使规划无故过期，回写也不能覆盖他人新增的资料索引。树与两个路线图共享快照，布局和未提交编辑另存；旧连接或旧资料源的响应不覆盖新快照。

Agent 写入由可信工具上下文与活动 WorkRun 绑定约束，不能以模型自报节点、会话或授权字段扩大范围；运行中的工作保留启动基线，范围变化使用新绑定版本和接续记录。幂等重试先查询原回执，不能因原命令已经推进版本而误报冲突。具体协议见[架构的提交与同步设计](../architecture/2026-11-11-project-development-architecture.md#9-变更协议同步与恢复)。

路线图以公开项目资料保存，可按用户选择放在项目／DSH／自定义目录，供其他 Agent 读取和 Git 交换；显示语言、实际聊天与执行授权不作为共享规划传递。新机器沿用节点身份，Git 合并后重新校验依赖和完成条件；见[资料可移植与协作设计](../architecture/2026-11-12-project-data-portability.md)。

## 进展、完成与变化说明

路线图的主要进展依据是实际成果、验证状态、阻塞与剩余工作。子任务完成数可以作为线索，不能只凭数量比例推导里程碑已经达成。

Agent 拆出更多工作后，任务数量会变化；即使展示百分比，也应说明计算依据和范围变化，避免用户把重算误认为已完成成果消失。没有可信计算规则时，先展示“当前做到哪里、还缺什么”。

重大规划调整保留来源、修订和变化原因，用户能够比较前后目标、依赖与时间；不需要从开始就建设多版本排期引擎。暂停、取消、替代及未验证成果在两个视图中保持一致。

## 适合继续讨论的选择

- 首屏如何结合两种视角：可切换视图，还是目标卡片直接带时间窗口，再按需展开时间轴。
- 时间精度：版本／月份／周是否已够用，哪些场景需要日期、工期和日历。
- 变更日期时：只提示受影响目标，还是允许预览并提交一批联动改期；自动执行的授权范围如何表达。
- 首版边界：先做到里程碑与可选时间窗口，还是已有必须使用完整甘特图的真实场景。

这些细节通过本项目和真实代码项目试用收敛，整体设计已认可，当前不预先固定界面、首版范围或新的排期执行策略。中英界面与时间展示遵循[i18n 接入草案](../architecture/2026-11-12-plugin-i18n-design.md)，切换语言不重写规划内容或日期。
