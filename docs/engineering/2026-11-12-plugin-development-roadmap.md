# 项目管理插件开发路线图草案

日期：2026-11-12。状态：依据现有需求、架构和开工复核整理的实施建议，尚未定稿；没有活动实施 change，全部里程碑尚未实现、运行验证均为 `untested`。本文管理 dsh-cona 自身的开发，插件内的路线图功能另见[产品讨论](../product/2026-11-12-project-roadmap-design.md)。

## 目标与依据

交付集成在 DSH 内的项目管理插件，让用户与 Agent 共用长期规划，组织项目树、聊天、分析、开发规范、成果与模板。项目资料还须支持不同环境的多人 Git 协作、非 DSH Agent 直接读取，以及新机器 DSH 接续。需求来自[产品草案](../product/2026-11-11-project-management-design.md)，架构与数据协议分别见[总体架构](../architecture/2026-11-11-project-development-architecture.md)及[数据可移植草案](../architecture/2026-11-12-project-data-portability.md)，接入前提见[开工复核](../reviews/2026-11-12-dsh-rc2-development-readiness.md)。

本阶段固定 DSH `0.2.2-rc.2`，源码提交 `ddac96760b6edf8fa0fe17cbdcf0b512f4c12b2c`；在本插件第一个版本开发完成前不随上游更新。不自研 Agent 调度、沙箱或独立应用，旧文件恢复专题不作为开发前置。

下列 R1–R6 是本插件的新里程碑，与历史 Cona 的 M0 无关。当前只确定已有文档与静态核查事实，不把“设计已有”标为“功能完成”。先按依赖与交付成果推进；接入工作量尚无实测依据，暂不编造工期或发布日期。

## R1：插件贯通实验

先建立本仓独立构建与打包方式，固定 DSH 依赖，补充适合插件的构建、类型与必要测试检查。在独立测试 profile 中验证 Host、Client 模块和自有 Remote contribution 的加载，不借修改宿主核心来跳过第三方接入问题。

从第一个面板接入 DSH locale，建立本插件中英字典与插件管理页元信息。检查运行中切换、其他宿主语言回退英文、安装包含资源，以及切换不改变项目数据；具体方案见[i18n 接入草案](../architecture/2026-11-12-plugin-i18n-design.md)。

用最小 Project／WorkNode 聚合贯通持久化、聊天关联、Agent 工具与 UI。即使界面暂简，也从开始保存稳定身份、修订号，并允许节点与聊天多对多关联；当前执行目标单独绑定，避免后续重建身份和关系模型。

现行边界见[架构草案](../architecture/2026-11-11-project-development-architecture.md)：四层划分；公开 JSON／Markdown 与本机运行数据分离；项目／DSH／自定义目录保存同格式资料；规划用内容指纹核对，本机修订用于实例内同步；私有意图日志先于公开资料发布，结果待核对时不盲重放。不能继续套用早期“全部状态与回执放在一个宿主原子头”的设想。

R1 内先做公开格式与校验、独立包接入和文件提交，再做 Agent 贯通：前一步验证无 DSH 的资料阅读／校验入口、三种位置、Remote 往返、中英界面、资料头与私有意图／回执恢复；后一步接入真实会话和工具上下文，跑小树的自主调整与接续。领域规则可脱离 DSH 测试，Host 接口与文件失败语义另作运行检查。

完成标准：能重复演示“独立打包安装 → 面板显示小树 → 保存 → 打开关联聊天 → Agent 根据新信息在授权内新增或拆分节点并记录原因 → UI 显示已提交状态 → 重启恢复”，同时核查卸载清理和 Client 重连。保存失败、重复操作、过期修订、错误会话关联及浏览节点切换均有真实检查结果。

待在首个 change 中落实：包边界、构建配置、首版 schema、服务／工具接口、提交协议及测试环境。接入实验失败时记录具体失败和待改方案，再复核受影响里程碑。

以下场景纳入 R1 验收，当前全部为 `untested`：

| 场景 | 必须观察的结果 |
|---|---|
| 保存分析／执行记录后提交原规划建议 | 过程记录推进状态版本，不单独推进规划版本；规划未变时不制造过期冲突，真实规划变化仍被拒绝 |
| 命令提交后响应丢失，再重试或重启后重试 | 返回原回执、原生成 id 和原提交版本，不重复创建，也不因自身已推进版本而误报冲突 |
| 同一操作 id 携带不同参数或调用归属 | 明确拒绝，不执行第二次，也不泄露无权读取的原结果 |
| 公开资料可选项目／DSH／自定义位置 | 格式与业务一致，私有绑定、机器路径、聊天和回执不混入公开资料；实际位置可见且不静默迁移 |
| 正文、公开资料头或本机回执之间注入中断 | 未引用正文不作为发布成果；核对意图与文件内容，不能确定时保留待核对，不宣称跨介质原子提交 |
| 文件发布未知或本机存储返回 `unknown-state` | 受影响资料源停止写入；存储领域未知时停止其读写；界面标记待核对，不换 id 盲重试 |
| 模型伪造 Session／WorkRun／授权，旧绑定调用或排队请求到达 | 真实工具上下文决定调用归属，旧绑定不获得新范围；排队请求不覆盖运行目标 |
| 任务结束或取消后、Host 重启恢复 WorkRun | 保留实际历史与未知项，不仅凭恢复出的记录重新取得写入资格；可信身份不足的入口记为受阻 |
| 初次读取期间有新变更，或快照乱序／旧连接响应迟到 | 回读覆盖已知最新版本；旧代际和较旧状态不覆盖新状态，树与路线图显示一致 |
| 断线重连、提交后通知失败、旧回执返回 | 重新获取完整权威快照；已提交事实可查询，旧回执不回滚当前界面，未提交编辑得以保留 |

## R2：项目树、协作与工作接续

补齐用户直接编辑目标和完成条件、树移动与重排、分组／拆分／合并、复制、撤销／重做，以及流程子树插入。基础流程模板的存取与实例化在此完成，R5 再完善提炼、参数化和文件骨架。

用户和 Agent 使用同一变更服务。移动保留身份、聊天、成果和历史；复制创建新身份，不继承完成状态或授权。展示顺序与执行依赖分开，依赖环和非法移动由程序拒绝。

补齐项目概览、相关聊天导航、按当前工作组织的上下文和换聊天接续。一次工作可以明确覆盖多个节点，关联聊天本身不授予修改所有节点的权限。对运行目标的修改有明确接续记录。

以同一规划支撑路线图浏览，具体目标／时间视图按后文安排推进。树、路线图和对话入口的固定文案同步提供中英版本，日期格式变化不改变目标日期。

跨分支里程碑引用原节点或成果，保持单一身份和自身完成条件；交付关联不自动生成执行依赖。检查移动后关联保留、取消／替换后待核对、引用失效、同一成果用于多个交付，以及引用全部完成仍不足以证明里程碑达成的情况。

用不同目录的两份工作副本模拟不同协作者：一方只用公开说明和非 DSH Agent 阅读／修改 JSON 与 Markdown，另一方用 DSH 接入同份资料。验证 Git 合并后原项目／节点 id 保留、相对引用映射正确、本机聊天重新绑定，且不需要作者机器的 DSH 数据库。R6 再做不同实际开发环境的完整试用，不以双目录模拟代替跨平台证据。

检查两分支计数相同但内容不同、文本合并成功却依赖成环、未提交文件变化、索引新增被旧快照覆盖、回退分支后旧回执不重放、两个 worktree 绑定混用，以及位置迁移中断。冲突或未知格式保持可诊断且不自动覆盖，不自动 commit／pull／merge／push。

完成标准：用户手工搭建并调整一个开发流程，Agent 在授权范围内继续调整；节点和聊天的多对多关系可查询，手工修改不被旧规划覆盖；新聊天能取得有来源的目标、约束、成果与未解决事项。检查并发编辑、移动丢关联、复制继承旧状态、撤销覆盖后续修改及点击节点改变执行目标等反例。

## R3：项目分析与自主规划

提供专门分析入口，记录范围、工件与规划基线、读取覆盖、事实、推断、建议及来源。首次接入已有项目和开发中复盘使用同一路径；不默认常驻后台分析。

分析结果与规划应用分开保存。Agent 可以依据新材料，在已有授权内新增、拆分、重排或取消工作，并合并展示原因；目标扩大或推翻明确决定时按实际影响集中提出选择。

分析与接续资料支持用户选择发布可移植摘要、来源与覆盖范围；原始私有聊天和临时材料不默认共享。接收外部验证或决定不当作当前机器复测或新增授权。

完成标准：对一个已有代码项目分析并保存发现，开发中改变代码或规划后再次分析；过时建议不能覆盖新修订。检查不完整阅读冒充全审计、分析顺带改代码、反复拆分和运行目标被静默改写。

## R4：开发、SDD 与成果

接入实际可用版本的 OpenSpec，建立项目节点与 spec、change、tasks、验证证据的多对多引用。工件正文及 tasks 的权威状态留在仓库，插件提供关联与投影。

引用以逻辑仓库及相对位置表达，新机器按本机工作副本解析；共享项目约定与个人 SDD 提醒选择分别处理，Git 拉取不能重开用户已关闭的提醒。

把讨论、分析和实施意图落实到工作接续，记录代码成果、实际验证、遗留问题与下一步。实现可关闭并持久保存的 SDD 提醒；默认值和设置范围在本阶段的设计中明确，提醒不改变仓库已有门禁。

完成标准：一个功能从讨论到实现、验证、change 归档后仍能查到成果及来源；简单任务可按项目约定直接处理。检查提醒关闭后重启／新聊天仍关闭、单次跳过不反复催促、工件移动与归档导致引用失效，以及 tasks 勾选或轮次结束冒充功能完成。

## R5：从零立项与模板

以普通 DSH 聊天完成需求调研、竞品对照与范围收敛，再形成可修改的规划。逻辑项目可先于代码目录存在，需要文件工作时再准备目录与 Workspace。

完善预设与用户自建流程、模板版本、从已有项目提炼结构及参数化筛选。文件骨架独立记录计划、冲突和执行进度，既可在创建项目时应用，也可在后续节点应用。

内置模板名称、说明和预览提供中英资源；实例化后已成为项目内容的文字保留原文，界面切换不覆盖用户修改。

完成标准：用一个从零项目完成“调研 → 规划 → 选择模板 → 准备目录 → 开发”的过程，并在已有项目后续阶段再次应用模板或骨架。检查无来源竞品结论、模板泄露私密内容、覆盖已有文件、中断重试重复生成和把计划中的目录显示为已生成。

## R6：首版试用与交付

将各切片连成完整使用过程，至少走完一个从零项目与一个已有代码项目。优先记录重复说明背景、错误关联、上下文噪声、误入实施、规划过细、变更冲突和恢复成本，再调整默认规则。

完成标准：交付可复现构建的安装包、安装／卸载与升级说明、数据格式与迁移说明、已验证环境和已知限制。重新核查失败与恢复、权限边界、生命周期和持久化；围绕实际目标平台补充路径语义和运行验证，未测平台不宣称已验证兼容。纯 Node ESM、跨平台设计边界继续有效。

完成至少两个实际开发环境间的资料交接，记录不同 Agent 阅读、Git 冲突处理、新机器 DSH 接入、位置选择及迁移的结果；公开格式、版本兼容、共享内容范围和本机残留分别说明。

核查全部已交付界面的中英资源、英文回退、长文本与时间显示，以及真实安装包中的资源和重启后的宿主语言选择。现有文档双语门禁不替代产品 i18n 验收。

必须验收场景有失败或受阻时，不以缩小表述冒充通过；明确问题、影响范围和后续处理。机器测试、Agent 自查和用户试用分别记录，只有项目明确要求人工验收的事项才以人工结果作为完成条件。

## 路线图功能的实施安排建议

2026-11-12 用户已认可项目树、目标路线图和时间路线图共用规划的整体设计。具体设计见[路线图功能草案](../product/2026-11-12-project-roadmap-design.md)，以下是实施建议，具体界面与排期规则仍待细化。

建议先用本项目的 R1–R6 检验概念，再按以下依赖安排：

- R2 的稳定节点、依赖、完成条件与项目概览，为路线图共用数据提供基础；可在此试做里程碑视图。
- R3 的带来源规划变更用于解释路线图为何调整，以及调整是否影响当前执行。
- 目标日期、时间窗口、时间轴拖动和依赖改期策略先做交互试验，再确定进入哪个 change；不从“需要路线图”直接推导出完整甘特图或自动排期要求。
- R6 的试用根据已明确的路线图范围检查树、路线图及 Agent 读取的一致性。

## 开工与维护方式

下一项可执行工作是为 R1 建立首个实施 change，明确交付与反例后再落代码。本路线图不替代 change 的 proposal、design、spec 和 tasks，也不要求小修复全部建立完整流程。

每个实施 change 标明服务哪个里程碑；一个里程碑可由多个 change 完成。完成后把代码版本、实际验证、未解决项和下一项工作回写到本路线图；详细运行证据保留在本机，手写结论进入对应文档。状态始终区分计划、实现和验证，不凭任务勾选推断里程碑完成。

影响顺序、依赖、范围或完成标准的发现先记录依据，再更新路线图；涉及用户已明确目标时沿用既有授权边界。R1 取得实际工作量与风险证据后，再讨论是否需要目标日期或工期估计。
