# 项目数据位置、跨 Agent 读取与 Git 协作设计草案

日期：2026-11-12。状态：用户已明确多人、不同开发环境及不同 Agent 的协作需求，并要求保留数据位置选择权。本文件据此修订存储方案；格式、迁移与协作协议尚未实现，运行验证全部为 `untested`。

## 用户明确的需求

- 一个项目可能由多人在不同开发环境中合作，不要求所有参与者使用 DSH。
- 数据可以放在对应项目目录，通过 Git 管理；也可以放在 DSH 数据目录或用户自定义目录。
- 项目资料保留其他 Agent 的可读性；另一台机器的 DSH 取得这些资料后可以直接接入项目。

因此，原先将全部项目状态和运行回执放在一个宿主权威头的方案需要调整：**可移植项目资料是独立的公开文件协议，DSH 是它的一个接入实现；运行身份、私有记录和本机缓存另行保存。** 不将这项需求扩展为实时协同服务器、分布式任务调度或共享网络目录多写者支持。

## 数据位置由用户选择

| 位置 | 用法 | 边界 |
|---|---|---|
| 项目目录 | 资料随工作副本保存，可由 Git 提交、分支和合并 | 是否纳入 Git 由用户决定；不自动提交或推送 |
| DSH 数据目录 | 保留本机项目，适合无代码目录的早期规划或个人使用 | 同样使用公开资料格式，不以 DSH 私有数据库作为唯一读取入口；跨机需实际复制或同步资料 |
| 自定义目录 | 指定任意明确授权的数据根，可供个人管理或外部同步 | 不因目录可被多人访问就承诺并发写入安全；本机绑定与共享内容的规则不变 |

三种位置保存相同的可移植格式，不是三套项目模型。创建或接入时展示实际位置和 Git 跟踪状态；已有选择不因发现仓库元信息而被静默切换。没有代码目录时可先选 DSH 或自定义位置，后续迁移到项目目录。

用户选择的是资料位置，不是把所有 DSH 数据一并搬过去。本机运行数据默认留在独立的用户存储，也允许指定本机数据根；若用户把该部分放在项目目录内，应放入明确区分且不跟踪的区域。具体默认子目录名和设置入口在 R1 确定。本仓现有 `.dsh-cona/` 是实验产物约定，不因此成为插件部署目录。

## 可移植资料与本机运行数据

| 可共享、可移植的项目资料 | 留在本机的运行数据 |
|---|---|
| 稳定项目／节点 id、目标、树结构、依赖、交付条件、路线图与目标时间 | 本机绝对路径、Workspace id、DSH 安装身份与工作副本映射 |
| 项目工作约定、选定的流程模板及来源版本 | 实际 Session／消息 id、当前执行绑定、授权与取消终态 |
| 用户选择共享的决定、分析摘要、接续说明与成果引用 | 私有聊天、未发布草稿、临时分析材料和原始运行日志 |
| 明确发布的验证结论及受检对象／版本和适用范围 | 私有命令意图日志与回执、连接状态、视图布局和可重建缓存 |

共享结论是带来源和适用范围的项目事实，不是其他人的执行授权。导入“测试通过”不等于当前机器已经复测；缺少证据或本机无法解析的来源保持可见并标注未核查。用户选择发布哪些摘要，不能把完整聊天或私有资料默认写入 Git。

参与者和作者标记仅说明来源，不是认证主体。导入他人的数据不会赋予工具权限、接管其会话，或自动开始工作。

项目工作约定可共享，个人偏好与会话授权仍在本机处理。例如用户已关闭 SDD 提醒，拉取包含不同建议的项目文件不得静默重开个人选择；项目规则、个人覆盖与仓库已有门禁分别解释。共享正文里的指令、脚本或远程引用都作为资料读取，接入项目不自动执行代码、安装依赖或获取外部资源。

## 其他 Agent 可以直接读取的格式

首版建议使用普通目录、UTF-8 JSON 与 Markdown，并随格式提供 schema 与阅读／编辑说明。下面是结构示意，目录名和拆分颗粒度不在本轮定死：

```text
<project-metadata>/
  README.md           # 阅读入口、权威来源、格式版本和修改规则
  project.json        # 项目身份、格式版本、规划及已发布资料索引
  records/            # 可共享的决定、分析、接续说明和成果记录
  templates/          # 需要随项目携带的流程或模板引用
```

`project.json` 是结构化规划的权威文件；Markdown 记录承载自身的正文，规划文件保存引用与观察版本。README 主要说明如何读取和修改，不维护第二份可独立编辑的任务状态。若生成概览或路线图 Markdown，须标注其为投影及生成基线，不能与 JSON 并列为另一份规划真源。

节点以稳定 id 组织，展示顺序显式表达，序列化顺序和格式保持稳定，减少 Git 无关差异。完整聊天、运行数据库、凭据或依赖 DSH 才能解码的二进制不是资料协议的必需部分。

其他 Agent 不启动 DSH 即可阅读上述文件。需要修改时按同一文件协议操作，并可使用不依赖 DSH 运行时的格式／领域校验入口；该入口复用纯领域核心，不加载 React、Cordis 或模型服务。公开格式须版本化，未知的新格式不能被旧版本插件静默重写。第三方修改也要核查 id、树、依赖、交付引用和完成条件，不能仅因 JSON 可解析就接受。

接入说明可以由用户引用到现有 `AGENTS.md` 或其他 Agent 的入口文件，不自动覆盖仓库已有规则。共享相对路径按声明的资料根／逻辑仓库解析，不以当前进程目录碰运气；越界路径、符号链接指向、大小写及不可用工件均按访问范围核查。不同平台的磁盘拼接交给跨平台路径适配器，公开引用不携带系统盘符或本机分隔符约定。

## 另一台机器的 DSH 如何接入

1. 用户克隆仓库、复制资料目录或把自定义目录同步到本机，再由 DSH 发现或选择该资料入口。
2. 校验格式、稳定项目身份及领域规则，读取已有节点和已发布资料，沿用原项目／节点 id，不创建一份失去关联的新项目。
3. 依据当前工作副本为逻辑仓库／工作目录建立本机映射；资料中的代码、spec、change 和成果使用仓库标识与相对引用，不保存作者机器的绝对路径。
4. 为本机注册或核对 Workspace，并新建／关联本机聊天；从共享目标、决定、成果和接续记录组织上下文。外部 Session 引用保留来源信息，但不冒充本机可打开的会话。
5. 在真实请求边界建立新的 WorkRun 与执行绑定；导入的授权、运行状态或回执不直接恢复为本机写权限。

本机映射按项目 id **及独立的资料实例／工作副本身份**区分，不能仅以项目 id 将两个分支工作副本的缓存、聊天和活动执行混在一起。移动资料位置通过迁移更新绑定；独立复制为新项目则显式生成新项目身份。发现多个候选资料源时先让用户选择，不按同名路径自动合并。

“直接接上”是取得资料后能读取和继续工作，不表示插件已经提供云同步，或能恢复未共享的聊天与进程。

## Git 分支与版本语义

Git 管理资料文件的历史与分支。每个参与者在自己的工作副本中修改，通过已有 Git 工作流交换资料；插件保存文件本身不自动执行 commit、pull、merge 或 push。

跨机器不能比较自增整数判断新旧：两个分支都可能有“第 8 次修改”。因此版本分为：

| 标识 | 范围与用途 |
|---|---|
| `schemaVersion` | 公开资料格式版本 |
| `planVersion` | 按格式规定的规范化规划内容计算的指纹，作为跨环境规划基线；不代替业务校验或授权 |
| `planRevision`／`stateRevision` | 本机资料实例内的规划／查询状态顺序，重启延续；不作为 Git 分支间的大小关系，也不导入他人的计数器 |
| 资料实例／源代际 | 区分本机工作副本、迁移和重载边界，使旧绑定、旧响应不能写入或覆盖新资料源 |

规划内容指纹排除机器路径、运行记录及排版噪声，包含目标、节点、依赖、完成条件和时间等实际规划；准确规范化规则与样例在格式 schema 中确定。有序列表仍保留语义顺序，不能为了格式稳定而任意排序。Git HEAD 无法代表工作区未提交的规划文件，mtime 也不能独立充当版本。

每次读取／提交前核对当前资料源；外部文件变化要重新读取、校验，并更新本机状态。命令同时核对资料实例／源代际与 `planVersion`，本机计数器辅助同步。仅新增分析记录时重新取得最新索引并保留该记录，不能因为保存旧规划快照而将其覆盖。

文件适配器还保存本次观察的资料头和引用记录内容指纹，用于核对完整读写基线；它与仅包含规划内容的 `planVersion` 用途不同。共享记录发生变化时，即使规划指纹未变，也不能用旧索引覆盖新记录。规划指纹由读取方按公开规则重新计算，不盲信文件内自报的版本值。

检测到 checkout、merge、外部编辑或资料位置变化导致规划或执行基线变化时，先使旧快照和绑定进入待核对状态。存在冲突标记、格式不支持、树环或悬空引用时保留诊断和本机未提交编辑，停止对该资料源的写入，不用内存旧版本覆盖磁盘。即使 Git 文本自动合并成功，也必须重新做领域校验。

首版仅承诺单个本地资料实例由一个插件写者管理；Git 写入与插件保存须在明确的同步／重载边界顺序进行。提交前重读与内容核对不等于消除所有外部写入竞态，不宣称支持同一目录内任意进程同时改写，或多人同时写网络盘。

## 可移植头与私有回执的提交

资料文件不能携带运行授权和私有回执，因此不能继续假定公开规划与本机回执可在同一个物理记录里原子替换。修订为：

1. 核对调用身份、原回执、活动绑定、资料实例和当前规划基线；为新命令构造候选规划和稳定生成 id。
2. 在本机存储持久保存命令意图，包含原资料基线、候选内容指纹、生成 id、请求摘要和归属，再尝试发布资料头。共享正文若独立保存，先写正文，再发布引用。
3. 发布前重新核对源内容与写入资格；通过文件适配器替换资料头，再完成本机回执、版本和通知。整段过程按本机资料实例串行组织，但不称为跨目录／跨后端事务。
4. 崩溃恢复后若当前资料准确对应候选发布内容，可记录“内容已达成、经恢复核对”并补齐回执；这不单独证明是谁执行了修改或文件外动作已完成。若已有明确完成回执，则只返回历史结果，不重新应用到当前 Git 分支。
5. 若不能证明是否曾发布，或资料已被 Git／其他编辑改变，保留原命令为待核对，不盲目重放、换 id 或撤回他人的修改。即使当前内容又等于旧基线，也可能经历过发布再回退，不能直接当作“从未提交”。

这是意图日志与恢复协议的设计要求，须用中断注入验证，不能因采用 rename 或 `storageDomain` 就宣称实现了跨介质原子提交。回执去重范围是原本机资料实例及操作归属，不宣称跨所有协作者的全局恰好一次执行。

## 存储适配器与迁移

公开资料统一使用文件协议；项目目录、DSH 目录、自定义目录只改变其解析位置。`storageDomain` 继续作为本机注册表、意图日志、回执或缓存的候选，不能把其内部格式当成其他 Agent 的必读协议。

rc.2 的 `ctx.storageDomain.open(spec)` 接受领域声明，后端按领域名路由，根目录来自后端配置；没有由此证明可以为每个 Project 任意传入目录，也不应为本插件改掉其他宿主领域的数据根。项目／自定义文件位置由独立文件适配器验证，保持纯 Node ESM、跨平台路径语义，并仅写用户选择的数据范围；Host 直接读写不自动继承会话沙箱。

静态依据：[领域存储与路由](https://github.com/deepseek-ai/deepseek-harness/blob/ddac96760b6edf8fa0fe17cbdcf0b512f4c12b2c/packages/storage/storage-domain/README.zh.md)、[存储后端配置](https://github.com/deepseek-ai/deepseek-harness/blob/ddac96760b6edf8fa0fe17cbdcf0b512f4c12b2c/packages/storage/storage/README.zh.md)。本次未运行这些接口。

切换位置显式展示源与目标：保存未提交编辑，暂停该实例写入，复制可移植资料并校验，更新本机定位与源代际，再开放新位置。项目／节点 id 保留；旧数据不自动删除，不双向维护两份权威规划。复制中断、目标已有内容或本机运行数据需要迁移时分别核对，不把聊天同步混入资料位置迁移。

## 实施与验收

R1 验证三种位置的同格式读写、公开／本机分离、源基线和意图日志恢复；R2 用两份不同路径的工作副本验证 Git 往返、外部 Agent 阅读及修改、新机器接入、冲突与语义错误。R3–R5 分别完善可共享分析／接续、OpenSpec 相对引用和模板资料；R6 完成不同环境与完整安装包的试用。

必须检查：无 DSH 也能理解资料；新机器接入保留项目和节点身份；两台机器的相同整数修订不被误认；外部追加记录不被旧快照覆盖；Git 文本无冲突但依赖成环时拒绝写入；恢复旧分支不重放旧命令；私有会话、机器路径和授权不进入共享资料；选择与迁移不静默改变数据源。所有项目当前均为 `untested`。
